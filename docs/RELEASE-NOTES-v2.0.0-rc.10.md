# OntologyEngineering v2.0.0-rc.10 — 读图由学科知识驱动

**读图的判断写成了知识：制图概念目录、识别知识卡和逐概念的覆盖表决定程序怎么读，每个表达写明它对应哪个制图概念；读不懂的如实留下，不猜。**

这是 v2.0.0 的第 10 个整合候选（预发布，重构中）。rc.8 增加了读懂已有工程图纸，但识别规则是在一张开发图纸上校准的，换一张图就有大量内容读不懂。rc.10 把制图知识从代码里提出来，让知识驱动识别；同时修正 Project 管理程序的一处兼容缺陷，已记录的复核不再因重新编译或升级而打不开。

## 这一版有什么

| 内容 | 位置 |
|---|---|
| 制图概念目录：987 个概念，整理自国家标准和教材；每个概念一张卡，写明含义、组成、常见画法、DXF 形式、判别方法、易混项和出处 | `crates/oe-drawing/knowledge/concepts/` |
| 识别知识卡：21 张，写明一个符号由哪些部分组成、有哪些画法变体、反例是什么、用什么参数判别。程序按卡中的词表和参数判断，每个变体和反例都有对应测试 | `crates/oe-drawing/knowledge/drawing-representation.toml` |
| 覆盖表：每条规则和约定覆盖哪些概念，完整还是部分，缺什么。概念状态由表和卡推出，测试核对，不手填 | `crates/oe-drawing/knowledge/recognizer-coverage.toml` |
| 读图结果带概念：每个表达有 `concept_ids`，检查页显示概念名称 | `oev2 drawing route` 的关系图与检查页 |
| 已记录的复核保留当时的执行身份：重新编译或升级后，恢复和继续携带同一份复核的提交不要求同一程序；新增的复核仍由当前程序执行 | `crates/oe-engineering/src/project_workspace/` |
| 安装器直接使用 `rust-toolchain.toml` 固定版本的编译器，不受 PATH 中其他 Rust 和自定义 `CARGO_HOME` 影响 | `scripts/install.sh` |
| 说明 | [读懂已有工程图纸](DRAWING-UNDERSTANDING.md) |

## 新读懂的内容

- **尺寸**：角度单位、尺寸符号与偏差的文字形式；☆ 等特殊特性记号并入被标尺寸；方框理论正确尺寸；尺寸线越过终端把数值写到外面；分段画的尺寸界线和共用界线。
- **几何公差**：旧版与现行基准符号；用散线或整块图块画的框格及嵌套符号；Ø 公差带修饰；指引线落在轮廓延长线上。
- **表面结构**：旧版与现行代号，旋转插入，数值单独书写，所立的延长线。
- **视图与剖切**：剖切符号、视向箭头（含图块形式）、局部剖波浪线、手画的剖面线、放大图圆圈打断的轮廓。
- **其他**：技术要求、标题栏各栏、型号尺寸表、中心孔符号。

## 覆盖到哪一步

987 个概念中，卡识别 88、规则识别 6、部分 42、未识别 851。常见程度为“高”的 181 个概念中，卡识别 76、规则识别 6、部分 33、未识别 66。未识别的概念按常见程度分批推进；相应图元留在“未解释”，不猜。

## 效果

在两张开发用图纸（不随仓库分发）上：

- 用来修规则的第二张图：未解释的表达从 91 处降到 3 处，这 3 处都逐条查明了原因。
- 校准规则用的第一张图：未解释从 5 处降到 4 处，已有表达的成员没有变化。
- 专家指出的问题写成了卡中知识，不针对具体图纸；测试由卡中知识编写，不含这两张图的句柄和坐标，个别文字与图上相同的是标准写法（如中心孔标记）。

两张图都已用来写规则，以上数字不说明能用到别的图上。

## 独立测试

两个互不相看的 Codex 会话，从公开提交自己克隆、安装，独立读完这两张图，各用约 17 分钟，中途没有人工干预。读出的关系图与内部运行逐字节相同，专家纠正过的地方全部读对。这说明技能能被另一个客户端照文档走通，读图结果不随构建和客户端变化；分类由确定的程序完成，这不衡量 Agent 自己的判断力。这次测试针对合入前的分支提交；发布提交读两张图的结果与它逐字节相同，发布后另由日常配置的会话复核。

## 验证

- 锁定真实 ggen 重生比对 `consistent`、`drift=[]`，经验库合同 `matched`，八个程序按锁定依赖构建；从 GitHub 干净克隆发布提交后再次核对生成一致。
- 发布复核查出并修正两处问题：
  - 被测的分支提交有三个生成文件（`generation.json`、`model.ttl`、`source-map.json`）没有同步，从干净克隆跑 `design check` 报 drift；它们只记录源文件摘要，读图结果不受影响。
  - 恢复 Project 时，当前提交里的复核要求由记录它的同一程序重新执行，历史里的复核要求引擎版本等于当前程序，所以任何重新编译或升级都会让带复核的 Project 打不开，而且报错不说明原因。这与“版本更新不重签历史回执”的规则矛盾。修正后，已记录的复核只核原件、绑定、当前 Project 和聚合结论。
- 测试：工作区单元 5 项、来源缓存 3 项、工作区与任务视图集成 55 项（另 1 项 ignored）、复核接续 12 项、CLI 失败原因 8 项、读图 146 项、独立复核 2 项、读图 CLI 7 项、义务 6 项、engineering-memory-runtime 109 项（另 2 项 ignored），全部通过；ignored 的既有案例不计通过。
- 安装：在干净克隆上，用非默认的空 `CARGO_HOME`、PATH 里有其他版本的 Rust，安装器一次成功（这正是修正前会失败的情况）。
- 管理程序：在一个 286 次提交的长期 Project（不随仓库分发）的克隆副本上，本版与 rc.9 的完整恢复输出逐字节相同，本版写入的 `/6` 提交两者读出也逐字节相同；本机另外 15 个 Project 的克隆副本上，两者结果全部相同：12 个恢复输出逐字节相同，其中包括一个头提交带复核、修正前无法恢复的 Project；3 个两者都拒绝，原因与本版无关。

## 已知限制

- 识别结果是待复核的候选，不是工程采用。专家对这一版的复核尚未完成；能否用到别的图，要用没见过的图盲测。
- 读图仍只支持 ASCII DXF 的有限剖面与 macOS 上的隔离 worker，其余限制同 [rc.8 发布说明](RELEASE-NOTES-v2.0.0-rc.8.md)。
- 历史里的复核，如果它记录的影响与当前程序推导的不同，恢复仍会拒绝（`workspace_history_review_impact_changed`）。本机有一个 Project 在 rc.9 上就是这样，本版没有改动。
- 独立测试中两个会话都绕过了下面这些问题，读图结果没有受影响，留待后续处理：
  - 第一次提交 Project 时，图纸没有建立到根对象的关系会被拒绝，要单独运行 `project route-audit` 才能查出原因。
  - 依赖集合必须按规范顺序保存，否则报 `workspace_project_material_mismatch`，错误里没有指出原因。
  - `design evidence` 不接受 `--project-home`。
  - `project tool-result` 的 registry 相对路径按安装根解析；时间只接受 UTC 秒级 `Z` 格式。
  - 恢复时来源清单多列或少列都会被拒绝，错误里没有列出具体项。
  - 按图元的分类表没有标准导出，由 Agent 从关系图自行导出，范围可能不同（只列顶层图元，或连块内图元都列）。

## 安装与升级

```sh
cd "$HOME/OntologyEngineering"
git fetch --tags && git checkout v2.0.0-rc.10
sh scripts/install.sh
"$HOME/OntologyEngineering/var/install/bin/oev2" --root "$HOME/OntologyEngineering" --version
```

安装器保留上一安装为 `var/install-previous.*`，私有数据目录 `var/` 与 `sources/` 不受影响。已有工作区无需迁移。已打开的会话要重新打开才会加载新版技能和 MCP 服务。

程序每次调用都核对源码：切换源码之后、新程序装好之前，旧程序会报 `compiled_source_binding_mismatch`。如果有工作正在调用这份安装，先在别的目录编好同一提交的程序，切换源码时立即换上，再运行安装器。

本版不授予工程采用，项目的全部根验收仍按各自证据判断。
