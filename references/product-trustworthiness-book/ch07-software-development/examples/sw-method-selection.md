## 1. 先读懂表：§4.3 的三个符号与两类条目

**推荐等级**（每个方法×ASIL 一格）：

| 符号 | 含义 |
|---|---|
| `++` | 对该 ASIL **强烈推荐** |
| `+` | 对该 ASIL 推荐 |
| `o` | 对该 ASIL 无倾向（不推荐也不反对） |

**条目类型**（表左列编号决定组合规则）：

- **连续条目**（1、2、3…）：该 ASIL 下列出的 ++ 和 + 方法原则上都适用；可以用表外方法替代并说明为何满足对应要求。若一个整体理由已证明不选全仍满足要求，则不必再逐项解释遗漏的方法。
- **备选条目**（1a、1b、1c…）：按 ASIL 选**适当组合**（表外方法也可入组）；同一 ASIL 下不同推荐度并存时**优先选推荐度更高者**；所选组合（甚至单一方法）须给出满足要求的理由。

> 教学要点：++/+/o 不是"打勾清单"而是**论证的起点**。本节三张表的条目全部是备选条目，因此所选组合（即使只选一种方法）都要用 rationale 说明其满足对应要求；这不等于每个 ++ 方法逐项强制。我们的本体只把推荐等级建成可查询事实，把"选择是否充分"留给专家判断（门禁不越界）。

## 2. Table 7 单元验证：十四种方法的画像（1a–1n，备选组）

按推荐模式分四族读（完整矩阵见本体/原表）：

**全程 ++ 族（四个 ASIL 都强烈推荐）**：静态代码分析(1h)、基于需求的测试(1j)、接口测试(1k)——它们在各 ASIL 的组合论证中都是优先候选，但不因 ++ 而成为逐项强制。

**随 ASIL 升级族（A/B 推荐 → C/D 强烈推荐）**：半形式化验证(1d)、控制流分析(1f)、数据流分析(1g)、背靠背模型对比(1n)——ASIL 提高时这些方法应被更优先考虑。其中 1n 仅在存在能够模拟软件单元功能的模型时适用，模型与代码接受相同激励并比较结果。

**D 专属升级族（仅 D 升为 ++）**：故障注入(1l)、资源使用评估(1m)——在 ASIL D 的组合中推荐度升高，但仍不是由该表直接规定的单项强制活动。

**低 ASIL 特色族**：走查(1a)在 A 是 ++、到 C/D 降为 o，与审查(1c)在高 ASIL 下推荐度升高形成对照；形式化验证(1e)在 A/B 是 o、C/D 为 +。这些都是表中的推荐画像，不直接规定项目的最终组合。

> 教学要点：**走查与审查的推荐度互补**（A：走查++审查+；D：走查o审查++）是"备选条目按 ASIL 选组合"的一个直观示例——同一目的（人工评审），不同 ASIL 可形成不同强度的候选组合。

## 3. Table 8 测试用例推导（1a–1d）

需求分析(1a)全程 ++；等价类(1b)与边界值(1c)从 B 起 ++；错误猜测(1d)恒为 +。这些符号表达推荐度，而不是标准规定的固定主辅顺序。

> 教学要点：这张表回答"测试用例从哪来"。需求分析始终具有最高推荐度，等价类/边界值从 B 起具有最高推荐度，错误猜测保持推荐；项目仍须为最终组合给出满足 9.4.3 的理由。

## 4. Table 9 结构覆盖率（1a–1c）与 9.4.4 的闭环

| 度量 | A | B | C | D |
|---|---|---|---|---|
| 语句覆盖 | ++ | ++ | + | + |
| 分支覆盖 | + | ++ | ++ | ++ |
| MC/DC | + | + | + | ++ |

覆盖率的用法在 §9.4.4：**必须测定**需求覆盖与结构覆盖；覆盖不足时要么补测试用例、要么给出理由。资料性的 NOTE 1 提示"无目标值或低目标值且无理由=不充分"；资料性的 EXAMPLE 2/3 给出可用于构造理由的示例：可接受的死代码（如调试代码）、配置相关代码段、用检查等互补方法覆盖、依据最新技术水平。这些 NOTE/EXAMPLE 是理解指引，不是额外要求或穷尽清单。

> 教学要点一：覆盖率分析的价值不只是数字——它能暴露需求测试用例的缺口、需求本身的不足、死代码/去激活代码/**非预期功能**（EXAMPLE 1）。
> 教学要点二：MC/DC 只在 D 是 ++——覆盖率阶梯（语句→分支→MC/DC）正是 ASIL 阶梯在验证深度上的投影。

## 5. 与本书其他章的连接

## 6. 本体化视角：method-table 是第四类映射形态

前三类：判定表（Table 4/分解/TCL：输入→**唯一**输出）。方法表不同：**方法×ASIL→推荐等级**，输出是"论证起点"而非结论。因此本体化策略也不同：

- 已选十二张表的推荐矩阵全量转录为 `MethodRecommendation`（84+164=248 单元可查询：如"ASIL D 下哪些方法 ++"一条 SPARQL 即得）；
- 每个推荐单元用 `recTable` 显式绑定具体表，使查询能够按表区分同名方法的推荐等级；
- `methodEntryId`（1a vs 1）保留条目类型，携带 §4.3 的组合规则语义；
- **当前门禁只检查已编码的转录约束**（表完整性、推荐等级受控），**不裁决方法选择**——选择的充分性属于专家 rationale，这与"教学假设不冒充标准结论"同一纪律。

## 附节（R3b）：设计侧三张表——准则主题、架构原则、单元原则

来源：Part 6 Table 1（§5.4.3 建模/编码准则主题）、Table 3（§7.4.3 架构设计原则）、
Table 6（§8.4.5 单元设计与实现原则）。与验证侧（Table 7/8/9）互补：
**验证表管"怎么查"，设计表管"怎么写才好查"**。以下为教学重述（++/+ 依原表；完整矩阵见原文）。

### Table 1：建模/编码准则要覆盖的九个主题

全 ASIL ++ 的四件"地板"：低复杂度强制、语言子集（如 MISRA C）、强类型、命名约定。
随 ASIL 升级：防御式实现与可信设计原则（A/B 为 +，C/D 升 ++）；图形表示无歧义与风格指南（B 起 ++）。
恒为 + 的一件：并发方面——标准对并发的态度是"必须管，但怎么管留给项目"。

> 教学要点：Table 1 是"准则的准则"——它不规定具体规则集，而规定**你的准则必须覆盖哪些主题**。
> 选 MISRA C 不等于自动合规：还要检查九主题是否都被覆盖（如并发 MISRA C 覆盖有限）。

### Table 3：架构设计九原则

全 ASIL ++：层次结构合理、组件规模复杂度受限、调度属性合理、共享资源管理得当。
B 起 ++：高内聚、低耦合。**仅 D 升 ++**：接口规模受限、中断使用受限、组件空间隔离——
这三条正是"免于干扰"（FFI）的架构手段，与 §7.4.9 软件分区呼应（ch07 正文）。
NOTE 明示：诸原则非互斥，需**适当折衷**——原则表不是逐条打勾清单。

### Table 6：单元实现十原则

Table 6 自身全 ASIL ++ 的四项是：单入单出、变量初始化、变量名不复用、无无条件跳转。
Table 1 的命名约定同样全 ASIL ++，但属于建模/编码准则主题，不计入 Table 6 的十项库存。
B 起 ++：无动态对象（或创建时在线检测）、指针受限、无隐式类型转换、无隐藏数据/控制流。
C 起 ++：避免全局变量（或论证使用）、**无递归**。
NOTE 点名：C 语言下 MISRA C 覆盖了本表多数原则。

> 教学要点一："或 else"句式（无动态对象**或**创建时在线测试；避免全局**或**论证使用）是标准的
> 务实姿态——禁令可以用受控例外替代，但例外必须显式论证，与 §4.3 的 rationale 精神一致。
> 教学要点二：递归到 C 才 ++ 禁用而非 A 就禁——推荐度阶梯精确到条目，这正是方法表值得
> 本体化（而非当整页图片贴上）的原因。

## 7. 生命周期九表全景（R3-p6 批次：Table 2/4/5/10-15）

Table 7/8/9 覆盖单元验证；Part 6 的方法表其实贯穿软件开发全生命周期。九张表已全量转录进
`sw-method-tables.ttl`（41 方法/164 单元，三层闭世界门禁），按阶段读：

**设计怎么写（表示法）**：Table 2（架构，7.4.1）与 Table 5（单元，8.4.3）画像完全相同——
自然语言四个 ASIL 全 ++，非正式表示法 A/B ++ 而 C/D 降为 +，半形式化 C/D 升 ++，形式化恒 +。
两条教学要点：其一，当前两张表中自然语言在四个 ASIL 下均为 ++；这表明提高形式化程度
并不自动取消自然语言这一候选，但 ++ 仍是推荐等级，不表示每个项目都必须单独采用；其二，
画像相同不等于同一张表——作用域（架构 vs 单元）不同，本体中的两组推荐单元分别用
`recTable` 绑定所属表，支持按表查询。

**架构怎么验（Table 4，7.4.14）**：本批次新增的九张 Part 6 方法表中**唯一含 `o` 单元**的表；早先受控转录的 Table 7 也含 `o`。
走查在 A 是 ++，到 C/D 直接落 `o`（审查的推荐度同时升高）；原型生成与形式化验证在 A/B 是 `o`，
高 ASIL 才升为 +/++。`o` 不是"禁止"，是"标准对开展与否无倾向"——转录时把 `o` 与 +
混淆是一类需要检查的失真，因此当前矩阵门禁的期望等级编码为 Table 4 设了 o 例外分支
（当前登记 fixture 将走查×C 改为 + 后，由预期 Shape 报告违规）。

**集成怎么测（Table 10/11/12，10.4.2/10.4.3/10.4.5）**：Table 10 里基于需求的测试、接口测试、
资源使用评估、静态代码分析四项全 ASIL ++，是适当组合中的高优先级候选，不是四个独立强制勾选项；故障注入、背靠背对比、
控制/数据流验证 C/D 升 ++。Table 11 是集成层的用例推导：等价类与边界值 **B 起就 ++**。
Table 12 只有两行（功能覆盖率/调用覆盖率），且其要求条款 10.4.5 以 §4.4 括号语义
对 (A)/(B) 只是建议——覆盖率测定的强制性本身分级。

**整机怎么测（Table 13/14/15，11.4.1/11.4.2/11.4.3）**：环境（HIL/ECU 网络全 ++，实车 C/D ++）、
方法（基于需求的测试全 ++；故障注入仅 D ++）、用例推导（新增"功能依赖分析"与
"运行使用用例分析"两个嵌入式特有条目）。

对照读才见分寸：**同名方法，表不同则画像不同**。边界值分析在集成用例表（Table 11）B 即 ++，
在嵌入式用例表（Table 15）B 仍是 +（C 才 ++）；错误猜测在单元/集成层恒 +，到嵌入式层 C/D
升 ++（现场知识在整机层价值更高）。`CQ-CH07-07` 查询当前图中的前一组对照，返回两张表
各自登记的 ASIL B 推荐等级。这说明逐格建模支持直接查询跨表差异；当前查询结果不等于对
所有同名方法错配情形的拒绝证明。
