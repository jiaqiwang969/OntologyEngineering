# AI 时代的功能安全与知识工程
# Functional Safety Meets Knowledge Engineering
#
# 本书方法主线的立论：为什么用本体承载 ISO 26262。
# ==============================
# 1. 规范是"文档"，工程需要"知识"
# ==============================
# ISO 26262 十二部分、数百页交叉引用：条款引条款（"see 4.6"）、
# 表引条款、Part 引 Part。人读靠翻页与经验；组织执行靠模板与检查表。
# 断点在于：若关系只留在自由文本里，就难以做统一查询、约束和回归；这不是
# 说文档本身不可查询，也不是说结构化以后即可自动判断工程正确性。
# 本书的做法：把其中适合形式化的条款身份、表、关系和局部约束建成知识结构——
#   引用变成边（derivedFrom/allocatedTo/controls/…），
#   判定表变成映射单元（Table 4 / 分解方案 / TCL Table 3），
#   部分可机械检查的必填/唯一性/状态合同变成 SHACL 门禁，
#   已登记来源变成带 document/clause/page/block/bbox 的锚点。
# 标准中的 shall 不会因此“变成”数据库规则；直接规范要求、操作化、本书家规与
# 项目策略必须分层，门禁只能检查它实际编码的那一层。

# ==============================
# 2. 与 AI 工具链的关系（为什么现在做）
# ==============================
# 大模型让"读规范、起草工作产物"的成本骤降，但也放大了两个老问题：
# - 幻觉：生成的条款号/表值/结论可能是错的；
# - 漂移：多人多工具并行产出，术语与结构悄悄分叉。
# 本体化结构是对策之一：受控词表 + 有类型的关系 + 局部可执行约束 + 来源入口，
# 让进入受控范围的 AI 产物与人手产物接受同一组已声明合同（数量从当次运行清单派生）。
# 门禁降低一部分结构错误静默传播的机会，不检验未编码语义，不替代工程活动与批准。
# 本书写作过程本身就是案例：术语编号靠回原文核验（ch02 教训）、
# OCR 损坏数值结构化重建并留痕（ch06）、每个反例精确归因（ch08）。

# ==============================
# 3. 读者得到的两种能力
# ==============================
# 领域能力：理解一个教学相关项怎样把 HARA 结论交给后续安全生命周期活动，
#   并能区分候选结构、执行证据、评审接受与产品放行（明线，ch04→ch11）。
# 方法能力：面对另一部工程规范，能够从真实问题出发尝试概念化→关系显化→
#   局部约束→案例实例化→来源回查与回归，并公开未覆盖语义；迁移方法不等于
#   复制本书模型，也不预先保证形成完整本体。
