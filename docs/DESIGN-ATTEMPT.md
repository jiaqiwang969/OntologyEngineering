# A design attempt in the existing Project

Engineering ontology defines the meaning → actual ggen generates the shared contracts → Rust uses the existing engineering owners → later, bounded RRSI-inspired comparisons can examine evidence. This increment joins source preparation, independent intent and actual engineering work. It introduces no Project, source registry, model training, design-method evaluator or adoption authority.

## Freeze and recheck

`oev2 project design-attempt prepare --input var/attempt.json --output var/new-attempt` reads an `oev2.design-attempt/1` request. The agent writes this internal input from the user's ordinary engineering request. It refers to an existing inCAD preparation request and its complete output directory, plus a separately authored `oev2.design-intent/1` file. All references carry original byte SHA256; source files must be inside the explicit skill root except the read-only archive paths already admitted by the existing inCAD owner.

The complete original work/3, full current Project, Project context, independent intent, original supplier specifications and original exported task are frozen. The complete condition text and engineering-basis/1 or /2 are retained, including facts, unknown assumptions, source applicability, model boundaries, function continuity, counterexamples and parent goal support. The attempt calls the existing `engineering::checks_current`; it neither invents a second basis nor turns a declaration into physical truth. Existing unknown or violated premises remain visible and do not prevent recording a design investigation. Missing or changed source identity does prevent reuse.

The intent identifies the same object/revision/condition, states the proposed independent design, cites existing Project sources, and retains alternatives and unknowns. Independence here means separate frozen input before this record's execution: it does not prove that the author never saw a reference answer. Numerical units/tolerances and engineering assumptions remain in the original source/work/basis and later original CAD intent contracts; there is no implicit conversion or inference from a final model back to its acceptance criteria.

The tool plan contains work, Harness, CAD evidence, manufacturing handoff, formal review and feedback activities, each with required evidence and exact original acceptance text. Every work acceptance must occur in the plan. Full acceptance order and content remain in the frozen work, including obligations not yet supported by any result. A planned activity is not an executed one.

Reference exposure records whether a source was seen before freezing, afterwards, or at an unknown time. Source IDs must belong to the same Project. Current collected cases stay `development_replay`, including cases with no separate reference file in the model window. HTML, earlier conversations and CAD exposure cannot be erased by choosing another case number.

The terminal preparation is written after source rechecks. `project design-attempt verify --input var/attempt.json --prepared var/new-attempt` reopens original sources and checks every frozen file. Same-revision edits to conditions, decisions or adopted flags also change the full frozen Project and invalidate preparation. A later existing-Project registration of new evidence requires an explicitly rebound new attempt; it does not silently rewrite the earlier intent or inherit success.

## Execute and collect

`oev2 project design-attempt record --input var/record.json --output var/new-record` takes an `oev2.design-attempt-record/1` request pointing to that exact attempt and preparation. It really executes the existing local work owner: source retrieval, model applicability, calculations and any work handoff. No remote model or native CAD execution is implicitly launched. Existing source-request failures and arithmetic/application differences are retained. In particular `analysis_completed` does not prove a missing handoff, native model, formal review or manufacturing acceptance.

Optional artifacts map to frozen tool steps:

- `work_result`: retain a complete previous work result, including partial/failed work. Check its original work-input SHA, Project reference, object and complete acceptance. The recorded status is historical; the new work execution is separate.
- `harness`: call the existing `load_step`, checking all its original archive artifacts, the complete frozen Project bytes and current context. Loading does not repeat model execution or authenticate an author.
- `cad_evidence` / `handoff`: use the original CAD/source verifier with an explicit private source root and matching Project/model revision. Retain original native claims and failures. The legacy packet shape alone does not establish the attempt object's current condition association; the output says so. Native tool execution and independent reopen are not inferred from verified hashes.
- `feedback`: retain the complete author report with `author_report_only`. Words such as “success” or “no_delta” do not run tools, evaluate a method or promote knowledge.

An optional `DesignAttemptReview` supplies original Binding and evidence references, selected package, queries/shapes and optional prior receipt. It invokes the existing `RustSemanticPort` and `review_current`. Necessary checks, package/source identity, condition model, engineering premises and original prior identity keep their existing meaning. Failed or unknown review remains recorded. No imported “pass” object can substitute for this new execution.

The result contains all original artifact values, each owner's actual verification result, the new work result, review receipt/failure, engineering checks, later reference exposure and every remaining acceptance obligation. Artifact verification failures remain `failed/unknown`; they are not described as verified. A record always reports `design_complete=false`, `adopted=false`, and `engineering_conclusion=unknown`. Its terminal inventory proves a recording operation and byte identities, not a completed design. Current source rechecks occur before terminal publication. Private inputs use the existing 16 MiB per-file boundary and at most 64 MiB per frozen/recorded file collection; no data are truncated to fit.

## Current boundary and next evidence

The shared DTOs are generated from `specs/engineering.toml`; handwritten orchestration is in `oe-engineering::design_attempt`. Current actual generation, tests, CLI use and receiver checks require their own receipts. Existing inCAD preparation/work versions and their meanings are unchanged. The complete original library migration, native CAD implementations, manufacturing drawings, physical inspection and real-project delivery remain separate work.

An actual attempt should next supply a source-bound mechanism design and native execution inputs, obtain real CAD readback/save/independent reopen, assemble its manufacturing/inspection handoff, and review those outputs in the same Project. The existing Harness/experience flow can retain failures, user corrections and `no_delta` where supported. General design-method comparison and unseen transfer still need independent frozen criteria and their own executed evidence.

The actual CLI additionally saves exact `cli-input.json`, its real `execution-binding.json`, and finally `cli-completed.json`. This outer terminal binds those bytes and the immutable library `completed.json`; the two inventories have separate meanings and no hash cycle. A library-only terminal does not prove CLI completion. Verification is read-only and does not add a new completion to the original directory. Record-generated work results include the original work SHA and complete Project/object/acceptance binding, so a later record can retain a real partial or failed result as bound history without converting it to success.

CLI completion also saves `execution-recheck.json` from the same execution-binding owner under a distinct completion role. Normalizer source, compiled CLI identity, both generated contract bindings and executable identity are rechecked against the starting binding before the outer terminal is published. The starting identity remains a separate original record.

For a pair of controlled alternatives, [design comparison](DESIGN-COMPARISON.md) freezes the common parent task and each original child attempt, runs both existing work owners and compares actual model results without rewriting this record protocol or its completion meaning.


## Explicit CAD association /2

`project design-attempt record` explicitly dispatches `oev2.design-attempt-record/2` to the same design-attempt owner. This reference-only branch accepts the complete original Project/work3, their byte SHA256 references, the exact object/current context/condition-content SHA and the complete ordered work/basis acceptance list. It retains all six tool obligations and source exposure. Its independent intent remains unknown; it does not reuse `/1` independent-intent qualification. The original `/1` input, preparation, record and legal-IRI review semantics remain intact.

Original CAD evidence/handoff packets use the existing CAD/source verifier. Their project/model/configuration/reference state must match the current work. Selected RFC6901 packet values are retained with an explicit original acceptance index/text. This is a source-bound association declaration, not proof that a supplied claim satisfies an engineering requirement. Original native observations, units, tolerances, unknowns and source byte identities stay in the original packet and owner audit. `source_root` stays private and inside the selected root; binary sources retain the original streaming verifier budget. The record never starts CAD or a model.

The kernel alone constructs `ValidatedCadFocus` after checking the complete original Project bytes and current context. The public focus context is a declaration, never a deserializable verified capability. Its canonical JSON UTF8 is encoded losslessly as lowercase hex after `urn:oev2:cad-engineering-focus:2:` with an 8 KiB payload limit. Raw object identifiers, Unicode, revisions and context fields are not normalized or replaced. Full Project bytes include decisions/adopted changes that the old input-only context intentionally excludes. A caller-supplied focus must match every byte. The association declaration RDF is a separate source-identity graph; original CAD URNs/ABox remain unchanged.

`project design-attempt verify-record --input ... --recorded ...` rereads the current Project/work and every original packet/source, checks the immutable record inventory and compares the full current result. Missing/drifted sources, same-revision edits, changed condition bodies, other objects/scopes, acceptance truncation/reordering/edits and forged reference/independent qualifications reject reuse. Each result still says `engineering_conclusion=unknown`, `adopted=false`, `native_adapter=not_run` and `formal_semantic_review=not_run`. The original complete native-evidence adapter, formal review and engineering applicability/independent design obligations remain subsequent work. Per-file 16 MiB and collected-record 64 MiB limits remain distinct from the existing CAD binary-source streaming limits.


For `/2`, the same owner precomputes every original copy, result, declaration graph and complete terminal with a bounded pretty-JSON writer. Selected claim envelopes are metered before their original subtrees are copied. Each file is at most16MiB and the complete proposed library record, including `completed.json`, is at most64MiB. The actual CLI includes all four existing outer files in that same collection before creating its output directory; it rechecks current executable/source identity before publishing the terminal. Revalidation reconstructs exact required original bytes, declaration graph and complete terminal instead of trusting a caller-edited inventory. A normal CLI record includes all four bounded outer files; unexpected, incomplete or nonregular attachments reject. Their hash consistency is retained as a supplied execution record; the library association checker does not authenticate an imported executable receipt.
