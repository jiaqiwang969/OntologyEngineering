# 能力问题设计示例 - 制造领域
# Competency Questions for a Manufacturing Ontology
#
# 能力问题（CQ）是本体的"需求规格说明书"与"验收测试用例"：
# 本体建成后，必须能通过查询或推理回答全部CQ

# ==============================
# 1. 能力问题的三个作用
# ==============================
# (1) 划定范围：CQ覆盖不到的概念，不要建（避免过度建模）
# (2) 驱动设计：每个CQ都能反推出需要的类、属性与公理
# (3) 验收标准：CQ → SPARQL查询，结果正确即通过验收

# ==============================
# 2. 制造领域CQ清单（节选）
# ==============================
# 基础查询类：
#   CQ1  哪些设备可以加工铝合金？
#   CQ2  当前哪些设备处于空闲状态？
#   CQ3  工作单元A中有哪些设备？

# 关联推理类：
#   CQ4  任务T001与哪些已排产任务存在时间冲突？
#   CQ5  产品P001应推荐什么加工工艺？
#   CQ6  工单W001的工序先后顺序是什么？

# 约束校验类：
#   CQ7  哪些高功率设备没有配置冷却系统？（违反公理）
#   CQ8  哪些设备的维护记录超期？

# 统计分析类：
#   CQ9  各工作单元的设备利用率是多少？
#   CQ10 过去一个月哪类故障发生频率最高？

# 注：CQ1/CQ2/CQ4/CQ5/CQ6 在第9章实战系统中有完整实现

# ==============================
# 3. CQ → 本体元素的反推
# ==============================
# 每个CQ可机械地分解出本体需要的元素：

# CQ1 "哪些设备可以加工铝合金？"
#   类：    Equipment（设备）、Material（材料）、AluminumAlloy（铝合金）
#   属性：  canProcess（对象属性：Equipment → Material）
#   公理：  AluminumAlloy ⊑ Material
#   实例：  具体设备与材料个体

# CQ4 "任务T001与哪些任务存在时间冲突？"
#   类：    Task、TimeInterval、Conflict
#   属性：  hasTimeInterval、assignedTo、conflictsWith
#   规则：  同设备时间区间重叠 → 冲突（SWRL实现见第5章）

# CQ8 "哪些设备的维护记录超期？"
#   类：    MaintenanceRecord
#   属性：  hasMaintenanceDate（数据属性：xsd:dateTime）、maintenanceCycle
#   约束：  当前时间 - 上次维护时间 > 周期 → 超期（需注入当前时间）

# ==============================
# 4. CQ → SPARQL 验收查询
# ==============================
# CQ1 的验收查询：
#
# PREFIX mfg: <http://example.org/manufacturing#>
# SELECT ?equipment WHERE {
#     ?equipment rdf:type/rdfs:subClassOf* mfg:Equipment .
#     ?equipment mfg:canProcess ?m .
#     ?m rdf:type mfg:AluminumAlloy .
# }
#
# 验收判据：返回结果与领域专家给出的标准答案一致

# CQ7 的验收查询（约束校验类，期望结果为空集）：
#
# SELECT ?e WHERE {
#     ?e rdf:type mfg:HighPowerEquipment .
#     FILTER NOT EXISTS { ?e mfg:requiresCooling ?c }
# }
#
# 验收判据：结果非空说明数据或公理有缺陷，需修复后复测

# ==============================
# 5. CQ驱动的迭代流程
# ==============================
# 与领域专家访谈，收集CQ（10~30个为宜）
#   → 按"基础/关联/校验/统计"分类，剔除超范围CQ
#   → 反推类/属性/公理清单（见第3节）
#   → 建模（七步法，见 ontology-101-process.txt）
#   → 每个CQ写验收查询，全部通过即完成一轮迭代
#   → 新需求 = 新CQ，进入下一轮迭代

# 工程建议：
# CQ清单应与本体一起进行版本管理（如 cq/ 目录下逐条编号），
# 每次本体变更后自动回归执行全部验收查询（CI化，防止回归缺陷）
