# 从调查结论到工程问题
# From an Investigation Finding to an Engineering Question
#
# 本文件是 ch01 的历史语境素材池，不是 ISO 26262 内容，也不承担事故归因。
# 具体事实和技术结论须回到 NHTSA/NASA 官方调查材料；不得由事件时间线推导
# “该事件促成 ISO 26262 发布”。

# ==============================
# 1. 可保留的有限事实
# ==============================
#
# 2009—2011 年间，美国围绕车辆非预期加速开展大规模调查；NHTSA 邀请
# NASA 检查相关电子控制问题。官方结论应按其声明的车型、版本、方法和范围
# 阅读：在所检查范围内没有找到支持某一电子缺陷归因的证据，不等于证明所有
# 电子系统不存在任何缺陷，更不等于一辆产品已经获得功能安全放行。
#
# ch01 使用这段材料只为展示一个证据阅读问题：
#
#   有范围的“未找到”
#       ≠ 无边界的“不存在”
#       ≠ 没有主语、危害、配置和接受准则的“系统安全”

# ==============================
# 2. 把事后问题前移
# ==============================
#
# 功能安全实践会把事故调查可能提出的问题，尽量搬到相应生命周期活动中：
# - 分析对象和边界是什么；
# - 哪种失常行为在什么场景可能造成危害；
# - 风险判断依据什么数据、假设和评审；
# - 安全目标如何派生为系统、硬件、软件与接口要求；
# - 哪个配置接受了哪些分析、试验和确认；
# - 结论处于 Draft、Planned、NotRun、Accepted 还是其他状态。
#
# 这些问题的产物是可复查的工程判断与证据，不是“零事故”或“无缺陷”承诺。

# ==============================
# 3. 两类失效只是学习导航
# ==============================
#
# 系统性失效：与需求、设计、实现或过程原因以确定方式关联；治理侧重方法、
# 追溯、评审、验证、确认和变更。这里的“确定关联”不表示同一条件下必然复现。
#
# 随机硬件失效：源于具有概率分布的硬件故障；治理侧重适用数据、任务剖面、
# 故障分析、架构度量与安全机制。量化结果依赖模型和假设，不是抄一个手册值。
#
# 两类失效解释不同证据路线，但不是 ISO 十二个 Part 的唯一官方分类方式。
# 它们最终在同一系统接口、安全机制、配置和整车安全主张上合账。
