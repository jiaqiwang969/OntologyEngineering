# 专业能力在四环中的作用与结果交接

在当前问题需要电子设计、仓库调研、源码定位、逆向调查、数学计算或性能分析时阅读。先按[主方法](../SKILL.md)辨明对象、活动及依据关系，再选择专业能力；能力可以组合、跳过或反复查证，不要求每个任务调用全部工具。

## 在四环中如何讨论工具

| 环节 | 对专业能力需要作出的判断 |
|---|---|
| 工程本体论 | 此次研究的是物理对象、数学模型、源码、制品还是运行过程？工具将提供来源线索、计算、行为观察还是改进候选？这些产物能够支持哪项主张？ |
| ggen | 哪些输入、前提、对象/工具版本、覆盖和结果关系需要由既有规范与合同承接？生成物能检查哪些关系，还有哪些依赖 Agent 解释和专业验证？不因接入一个工具就新造平行 Project 或声称已有适配器。 |
| Rust 工程模块 | 按当前支持范围执行明确的检查和编排，专业操作沿各工具真实入口完成；结果及未知交回同一 Project。外部工具的实现语言不改变 v2 自有规则由 Rust 执行的责任。Agent 负责理解输入、调用和结果之间的关系。 |
| RRSI | 用实际反馈判断工具选择、信息取得、结果解释或实现是否需要改进。先保留可比基线、行为要求和判据，再比较有限候选；安装、调用成功和保存经验各自保留范围。 |

同一产物可能改变作用：源码片段先用于定位问题，后来成为待修改对象；一次计算可用于探索，也可在满足前提后成为校验依据。调用另一个工具复述同一材料，或导入同一测量，不会自动增加独立证据。判断独立性要看来源、算法、输入和观测过程的实际依赖。

## 按当前问题选能力

下表说明这些能力的常见作用，具体使用仍读取当前可用技能目录中的同名 Skill。六工具的上游安装、锁定版本、必要 diff、companion 和实际小案例见[专业工具安装与接入](../docs/TOOL-INTEGRATIONS.md)。软件版本、安装路径、精确命令、授权和恢复条件以所选版本及实际入口为准，不把历史图示的安装标记当成当前状态。

电子设计作为第七种专业能力，与原六项共用 Project、证据接收、kernel review 和
reviewed reconciliation。其配套 EDA、器件模型和接线 skills 属于专业能力内部。
专业工具保持原生执行身份，当前 Rust owner 执行共同工程合同；不需要按工具数量
复制内核模块。电子执行与独立核验的接续入口见 `electronics-design` 的
`references/capability-integration.md`，某一仿真范围通过不能代表 EDA 或实物全部通过。

| 能力及 Skill 名称 | 何时有帮助、返回什么 | 接续时要辨清什么 |
|---|---|---|
| 电子设计 · `electronics-design`（按需调用 EasyEDA、仿真、器件模型与接线 skill） | 将电子需求转为有条件的电路/PCB 候选，执行专业操作并返回网表、原生文件、模型及检查/测量原件 | 保持同一 Project 与对象/条件/来源；资料电路、目标产品、仿真与实测分开。旧 ISAC SHACL 仅在原范围作辅助检查，尚无专用 PCB Rust 适配器；DRC 无错不等于电路功能或制造采用。 |
| GitContribute · `gitcontribute` | 调查仓库、相关工作、issue/PR、贡献约束；返回有来源和覆盖范围的资料与线索 | 来源/版本/时间与覆盖、冲突资料及必要的当前性核验；无命中不等于不存在。读本地语料与联网刷新按实际操作区分。 |
| LeanToken · `leantoken` | 在明确选定的本地仓库中定位实现、测试和有限上下文 | 仓库与提交/脏文件身份、索引 generation、实际返回字节和必要原文；找到测试不等于已运行测试。LeanToken 承担源码检索，Lean 证明检查属于另一项能力。 |
| REA · `reverse-engineer-anything` | 研究发布制品、二进制、托管代码或运行时；返回静态结构、反编译、调用关系或限定行为观察 | 区分源代码、发布制品、重建表示与实际执行；猜测的函数含义须有相应依据。动态观察按目标进程、授权、环境和覆盖记录，静态结果不冒作运行事实。 |
| Jacobian · `jacobian-math` | 按精确操作合同执行计算、有限搜索或结构分析；部分操作可返回证书 | 输入映射、数学前提、单位、精确/近似类型、误差与证书的检查方式；一般计算结果不统称形式证明，条件数学结论仍需核模型对工程对象的适用性。 |
| SmokingGun · `smokinggun` | 定位静态复杂度候选，组织外部发现、导入测量并比较候选 | 静态发现、理论估计、真实测量、行为保持及采用判据分别判断。它不执行仓库工作负载；导入的测量保留原生产者身份。候选不直接成为瓶颈，差值也不直接成为采用结论。 |
| flameox · `flameox` | 分析已有运行原件，或采集已授权且有界的工作负载；提供 profile、基准、轨迹及覆盖/失败记录 | 分析、采集和重放分别标记，重放不是重新测量。命令、环境、输入、预算、完整/部分结果和资源清退保持；单次 profile 不证明改进或因果关系。 |

使用前核当前技能与相应 CLI/MCP 是否实际可用。CLI、MCP 和后端算法是不同的接入形态；没有某个 MCP 名称不能据此判定其 CLI 不存在。实际业务验收须有当次输入、调用和结果，接口曝光或固定程序摘要匹配只支持各自的安装/身份判断。缺少能力时保留缺项，按已有授权选择可用方法；不为补齐图中的方框隐式安装工具或启动服务。

## 结果回到同一 Project

### 回交命令

工具结果一律经 `oev2 project tool-result` 回到同一 Project，不由脚本直接改写 `project.json`：

1. **调用前**：`project context --input <Project> --object <对象身份> --output var/...` 取当前快照；被分析的代码或制品写成 `oev2.subject-manifest/1`（绝对路径与摘要）。
2. **调用后**：原始输出存进该 Project 的私有区（如 `var/projects/<id>/tool-results/<result-id>/`），写 `oev2.tool-result/1`，内容包括：
   - Project 快照，以及针对的决定与根验收项；
   - 工具身份（须与本机登记表一致）、被分析对象版本、输入与条件（不含密钥）；
   - 执行状态与 UTC 时间、原始记录；
   - 结论：`observed` 须引原始记录，`inferred` 须引记录或其他结论，`imported` 与 `unknown` 分开；
   - 量测、行为检查、覆盖范围与未知项。
3. **核验与登记**：`project tool-result verify` 重读原件字节，核登记表与当前程序字节，核对象修订、条件内容与来源。`register --revision rN --output <新 Project>` 只新增证据与"决定←证据"依赖：原 Project 不改，结论与采用不变，受影响的决定进入重审。采用仍走 `project adopt` 的独立批准。
4. **性能比较**：先登记基线结果，再登记候选结果，然后 `project tool-result compare`。只有工具、指标、单位、环境摘要、输入集摘要都相同，基线结束早于候选开始，双方行为检查通过且样本达到要求时，才给出 improved / not_improved。
5. **本机登记表**：`var/capabilities/registry.json`（`oev2.capability-registry/1`，私有），列出每项能力的固定版本、程序摘要和接入验收记录。`project tool-result registry` 会重算程序摘要；工具未登记、版本不符或程序已变时，结果会被拒绝。

失败与部分结果同样回交（`failed` / `partial` 并写明原因）。它们支持"继续调查或补验"，不支持决定。

**更新决定**：`project decide --project <Project> --input <oev2.decision-update/1> --revision rN --output <新 Project>`。

- 请求写明决定、结论（supported / refuted / unknown）、所依据的结果文件、引用的结论（`result_id#finding_id`，限 observed 或 inferred）、理由和成立范围。
- 每份结果都会重新核验，摘要须与登记一致。
- supported 或 refuted 至少需要一份已登记、针对该决定、带观察结论的结果，其对象与条件须与该决定一致；unknown 可以只写理由。
- 决定改绑到这些结果的对象修订和来源，写入新 Project 副本，采用不变。已采用的决定走采用流程；回执列出需要重审的下游决定。

**改版后补验**：被分析的文件变了，旧结果仍可核验，但不再支持决定（`subject_changed_since_run`）；对象修订变了，旧结果直接被拒。此时在当前版本上重新运行工具、登记新结果，再更新决定。交付前按[根目标锚定](goal-anchoring.md)用 /2 锚定确认交付范围。

调用前明确待决定事项、当前业务对象及修订、条件、依据缺口、验收和原始输入。工具版本单独记录。使用已安装 Skill 指向的既有接续流程，保持当前 Project 身份；需要明确选定 Project 时由 Agent 依据实际任务处理，不从目录名猜项目。

保存原生结果和来源定位，核输入、程序、输出的身份以及完整/部分/失败状态。Agent 据证据说明观察、推断、导入结论和未知各是什么，支持哪项决定；按现有 Project 合同登记实际依赖，再由相应原生检查、当前审查与采用合同处理。工具退出零或字段 `passed` 不自动写成工程支持或采用。

例如，LeanToken 找到一处循环，SmokingGun 提出减少重复分配的候选，flameox 可在授权范围内取得运行证据；GitContribute 或 REA 仅在来源、实现或制品关系仍有缺口时加入，Jacobian 仅在需要明确数学关系时加入。先固定原输入、环境和行为要求，再比较基线与候选。源分析推测、某指标下降、统计不确定性和最终采用分别报告；共享同一测量的多个报告不重复计作独立验证。

对象、条件或上游依据变化后，沿原 Project 的影响与复核机制重审受影响决定。新证据形成新修订，旧运行、失败和采用保持原身份。专业工具链是否完成，以当前问题需要的实际结果与检查为准，不以调用数量计完成度。

## 反馈与后续使用

过程与结果进入同一项目；可迁移的方法、失败和用户纠正交内置 engineering-memory，保留原时间线、条件、来源和因果未知。memory 是本系统模块，通过 `oev2 memory` 使用，无需另装 Skill；当前任务是否使用历史经验按需要决定，空库可以开始。历史候选在新任务中仍须核适用性，调用或曝光不记作收益。

### 与 engineering-memory 的接续

memory 召回只是待核候选，经 `oev2 project` 原生核验后才进入 Project：

1. **召回与交接**：有当前 Project 时，用 `oev2 memory session prepare` 绑定该 Project 文件、对象版本与条件，再用 `oev2 memory session handoff` 取出选定经验的 `engineering-memory.session-handoff/1`，存进 Project 私有区（如 `var/projects/<id>/memory/`）。
2. **核验与登记**：`project memory-candidate verify` 原生重核以下各项：
   - 交接声明未授予采用、不写 Project；
   - 经验摘要按 memory 的排序紧凑 JSON 重算；
   - 逐条重读原消息字节窗口，可解析时同时核角色与文字；
   - Project、对象修订与条件未变。

   `register --revision rN --output <新 Project>` 只加一项 `memory-candidate:<id>@r<修订>` 证据。
3. **不支持决定**：记忆证据不能作为 supported/refuted 决定的依据（Project 校验直接拒绝），不能关闭验收项，也不能充当工具原始记录。候选提示的检查，要用工具或原件重新取得证据，再经 `project decide` 更新决定。
4. **反馈**：`project memory-feedback` 生成 memory 自己的 `session-feedback/1`，其中 `result_project` 绑定当前 Project 文件；再用 `oev2 memory session feedback --input` 提交。helped/harmed 须附实际使用的原消息；曝光、未使用与无帮助都照实记录。
5. **过程回流**：`project memory-export` 列出 Project 文件、已登记的工具结果与记忆候选、决定请求与回执（含被拒的），格式为 `{id, path, sha256}`，供 memory 整理时作为工件引用。会话过程本身由 memory 的会话接入保存。

当反馈提示方法需要改变时，按[有证据的改进](regularized-evolution.md)区分任务解释、表达、实现及使用问题，冻结候选和比较条件。保持原目标、独立判据、完整失败与成本；各专业能力分别提供所需证据，不承担自动授予全项目通过或普遍方法收益的职责。
