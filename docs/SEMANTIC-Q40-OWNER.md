# Q40 through the existing code qualification owner

This increment connects the already implemented structured reason port to the existing real replay, independent evaluation, scope witness and source association chain. It does not change the textual reasoner algorithm or authorize the complete Semantica library.

`CodeArtifactEligibilityExecutor` remains the owner. The same selected POLICY/context points to an explicit `oev2.code-scope-witness-request/2`. The existing external driver dispatches an independent evaluator, which invokes the same fixed driver and the actual baseline/candidate runners. The old request/dispatch/report `/1`, six-case oracle and permitted associations retain their original checks and results.

The runner receives only the frozen invocation input. Profile `local-semantic-replay/2`, capability `semantic.reason-metadata/1` calls the generated `SemanticReasonPort::reason`. Its nested `CodeSemanticReplayOutcome` separates semantic success/refusal from process completion. A boolean iteration bound is rejected while decoding the request and never invokes the port; 23 other fixed refusals occur in the reason port. Only explicit known input/convergence conditions are classified. Resource errors, unknown contracts, crashes, timeouts and source drift stay failed/partial. Success includes the complete `SemanticReasonResult` and request identity. Refusal includes the actual nonempty diagnostic, phase, code and condition, without a partial result.

The independent evaluator links contracts and bounded IO, not the semantic runtime. Comparison `semantic_outcome/1` requires completed outer execution, the original runner/input/source/condition identities and necessary checks. It compares the full successful result or precise refusal. Only the serde diagnostic wording for the boolean iteration type is not fixed; the diagnostic remains nonempty and the stage, code, condition, actual boolean and port-not-invoked state are mandatory. This is not a generic expected-error exemption.

The fixed public oracle contains exactly the existing 40 source-derived cases: 16 successes and 24 refusals. They were derived from pinned original source, not observed by running the old Python runtime. They are exposed development replay. The separate arbitrary-integer control is not a forty-first case. The catalog supplies 27 API-subcontract, 11 DTO-wire-subcontract and 2 adapter-guard relations. In particular, an explicitly marked plain Python mapping is only a wire-guard negative, not proof of Python object equivalence. No backend dependency is promoted by inference.

The `/2` report wraps a shared full-scope observation whose internal schema is `oev2.code-scope-witness-observation/2`; the old `/1` validator rejects it. All 13,494 original identities remain present exactly once and whole behavior/eligibility remains unknown. Roles and observed states are derived from the fixed catalog and actual candidate slots, never accepted from caller claims. The `/2` association index wraps the original candidate-source inventory DTO and the same role observations. The existing small association receipt remains a reference receipt, and its referenced index has the explicit `/2` schema. Snapshot, mapping and source checks still use the actual candidate root; relative owner artifacts and driver process references retain their original root roles.

Generation evidence keeps its actual version. The source-artifact verifier retains the original generation `/1` branch and explicitly validates composed generation `/2` through the existing design source owner. The `/2` check must name the exact retained generation; all root/fragment identities, recorded compiled/current composition sources, original budgets, normalized design, field-source map and generated products are rechecked against the selected artifact and manifest. The independent driver does not substitute its own compiled normalizer capture for that of the selected source. This closes a real integration refusal found when current RC3/candidate receipts were sent to the previously `/1`-only verifier. It does not certify the native five-stage builder, compiler reproducibility or adoption.

The existing source-artifact build profile remains the common local replay build family. The invocation profile independently selects the new capability; it does not rewrite the baseline artifact or its source identity. The driver/evaluator root must still differ from both runner roots. The actual oracle path remains an immutable external copy, although the same expected data is public and exposed in development source. New current programs and descriptors are required; old six-case driver/evaluator binaries cannot be relabeled as supporting Q40.

The original limits remain: at most 128 fixed cases, the runner's complete invocation frame at most 1 MiB, the oracle at most 4 MiB, and the same 600,000 ms scope dispatch ceiling with its existing enclosing guard. Q40 freezes one repeat per case, a 10,000 ms case process timeout and 1 MiB output. It requires 80 baseline/candidate run slots. Programs are reused; no per-case build or source-tree copy is introduced. Actual full-source/process verification is retained, so performance and completion require measurement. Timeout must retain partial/unknown results rather than shrink the denominator or silently extend the budget.

A newly supported adapter may report `local_adapter_coverage_gain` when the old runner lacks the operation. This does not mean reasoning quality, industrial usefulness, reduced cost or whole-library eligibility improved. All original 19 modules, 19 protocols, 22 owners, the complete migration inventory and the 47 prior static clues retain their original obligations. Named-graph, group/nullability, complete Python value fidelity, full external/native closure and whole-code adoption remain separate work.

Verification must run current generation, the 12 source/outcome/scope tests, old six-case and metadata regressions, all-target compilation, a real fixed 40-case baseline/candidate comparison, fresh owner association and installed CLI checks under bound compiled identities. A private source draft or synthetic structural report proves none of those actual executions. Final guard failure leaves diagnostic files without claiming transaction rollback or accepted qualification.


## Owner publication and actual acceptance

The owner finalizer remains private and is called only from the existing execute path. It invokes the original candidate snapshot check followed by current-input checks, then rereads the retained index, validates the version/roles, and writes the final receipt with write-new semantics. Four focused tests execute these private functions against real temporary files: versioned wrapping, changed retained bytes, rebound role metadata, late input failure/read order, write collisions and failed results. Their objects are synthetic; they do not certify a witness, a source snapshot, a process, or the80slot comparison.

Two additional explicitly ignored integration tests require a newly prepared `OE_Q40_QUALIFICATION_FIXTURE`. They never fall back to the old S six-case fixture. The positive must invoke the actual owner once and verify the full `/2` index, all40cases, both real sides, original13494 identities, candidate-only source mappings and retained raw process references. The negative changes only its own private copies and must reject altered descriptors or a fully rebound incomplete scope request before dispatch. Missing fixture input is an explicit unmet prerequisite, never a skipped successful test.

The outer qualification context has a600000ms maximum, and the existing nested rule reserves30000ms around the scope dispatch. Actual owner preparation therefore uses context600000ms and scope570000ms or less. Keeping both at600000ms fails the existing contract. No budget is expanded for Q40; actual timing must be measured, and80 incomplete slots remain incomplete.

The actual layout keeps installed RC3/skill and its original runner as the baseline. The Q40 adapter/catalog and explicit generation/2 verifier are genuinely generated and compiled for the independent driver/evaluator first; only its full public source manifest and two programs are retained in one receiving root. The candidate then adds the actual owner-fixture assertions for both selected generation/2 receipts and their separate source roots, together with the matching acceptance documentation, and is generated/compiled again using the same shared target. The earlier /1-only driver and its rejected preparation remain historical failure evidence. These are real successive source snapshots, not a forged source identity or an artificial marker. The driver and candidate manifest digests must differ, so the positive test can distinguish candidate-only source mappings from the driver source.

The receiving root contains every earlier compiled manifest file and its mode, including generated contracts, runtime scope and oracle files. It excludes private var, sources and .git and carries no copied Cargo target. The new CLI may use this root as the version owner only after its compiled-source guard is checked against its own exact source; otherwise a current candidate root is required. Owner and independent driver roles must remain distinct in the recorded inputs even if their filesystem root is shared. An isolated current CLI owner root must not silently inherit the earlier driver's compiled identity. The actual Rust library integration test creates only its own small private input root and explicitly remains independent of both driver and candidate.
