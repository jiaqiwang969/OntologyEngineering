## 11.1 子门禁已经是绿的，为什么报告还是不能签？

评审会只剩最后一个议题。秘书把一份 JSON 报告投到屏幕上，文件名是
`20260813-r4-final.json`。报告没有漂亮封面，最醒目的却是两个互相顶撞的事实：名为
`capstone-three-items` 的子门禁返回 0，范围更宽的 `knowledge-model` 门禁返回 1；最外层状态不是
`accepted`，而是 `failed`。

项目经理先看见了前一个数字：“收官章自己的检查已经通过，后面那项可能只是别章的小问题。第11章
先签，剩下的以后补。”这句话很合理。它没有否认红灯，只是想把绿灯覆盖的部分先拿出来签。问题在于，
他准备签的究竟是“一个子进程返回 0”，还是“这个候选知识包可以作为全书发布候选”？两个句子的主语、
范围和验收合同不同，不能共享一个动词。

### 11.1.1 一份真实报告里的子绿与总红

先把报告本身能证明的事实抄出来，不替它补情节：

```text
status=failed                         full_run=true
release_mode=false
input_count=540                       duration_seconds=5112.9
capstone-three-items: returncode=0    duration_seconds=119.156
knowledge-model:       returncode=1   duration_seconds=4945.288
drift: added=[] changed=[] removed=[]
```

这些字段说的是同一次历史运行。发现集含 540 个输入；前后快照没有发现增、删、改；capstone 子门禁在
那次输入上返回 0；范围更宽的知识模型门禁返回 1；总裁决因此失败。报告没有保存两个子进程的标准输出，
所以仅凭这份 JSON 无法恢复 `knowledge-model` 当时究竟是哪一条用例、哪个 Shape 或哪个元门禁失败。
若后来有人给那个红灯补一个具体原因，他必须另找当时日志；不能把后来观察到的失败签名倒填进历史。

这正是收口报告的第一道边界。结构化字段让我们知道哪个门禁红了，却没有保存足够诊断文本让人重演
红灯的内部路径。报告是真的，信息仍可能不够。真实性与充分性从来不是同义词。

这里还有三个很容易被表面数字诱导的误读。`full_run=true` 在当前 runner 中只表示没有用参数跳过
`knowledge-model`，不保证程序在此前失败时仍会执行后续门禁；是否真的跑到哪一步，要读 `gates`
数组。历史这份报告的九项记录齐全，且 `knowledge-model` 位于最后一项，所以能证明当次九项都曾
启动并返回，不是 `full_run` 这一个布尔值替它证明。`input_count=540` 说明发现器当时登记了 540 个
输入，也不证明发现规则没有漏掉本应纳入的
第 541 个文件；“找到多少”与“发现边界是否完整”必须分开审查。`duration_seconds=5112.9` 则只是
运行事实，不给耗时最长的检查额外表决权：一项跑 82 分钟的红灯不会比一项跑 2 分钟的绿灯更“重要”，
也不会因为成本太高而自动获得豁免。

最外层裁决用的是合取语义，不是平均分。把必要门禁写成 `G1 AND G2 AND ... AND Gn`，任意一个
`Gi=false`，发布候选就不能写成 accepted；局部绿只能原样保留为局部事实。有人在会后补一句“这个
红灯与第11章无关”，也不能改变当次裁决，除非验收合同在运行前就明确定义它不是必要门禁，并以新
合同重新形成一次有身份的运行。事后挑掉不喜欢的红灯，不叫裁剪范围，叫改判规则。

`release_mode=false` 再画出一道边界：这次运行使用常规整书门禁集，没有加入只在 `--release` 下出现
的出版覆盖门禁。它已经因常规必要门禁为红而不能接受；即使九项全绿，也只能支持常规模式下的结果，
不能补写“正式出版 release gate 已通过”。未运行的更强合同不能从较窄合同的颜色继承结论。

把五行压成四个可签或不可签的句子，界线更清楚：

| 准备写进纪要的句子 | 这份报告是否支持 | 理由 |
|---|---|---|
| “那次 capstone 子进程返回 0” | 支持 | 有门禁 ID、退出码、耗时与同次输入快照 |
| “那次常规整书验收通过” | 不支持 | `knowledge-model=1`，总状态为 `failed` |
| “那次出版 release 门禁通过” | 不支持 | `release_mode=false`，该更强门禁集未执行 |
| “2026-08-14 重写期快照仍得到历史同一结果” | 不支持 | 历史报告不等于后来的文件状态 |
| “三个教学相关项已经满足 ISO 26262” | 不支持 | 门禁检查知识模型合同，不执行产品工程活动 |

收口桌上最容易丢的其实是两个坐标：时间与范围。时间至少分“那次历史运行”和“重写期诊断快照”；范围
至少分“capstone 窄合同”和“整书必要门禁”。两条轴一交叉，得到四个不能互相借结论的格子：

| 对象格 | 目前有何观察 | 可以写什么 | 不可以借谁的结论 |
|---|---|---|---|
| 历史 × capstone | `returncode=0` | 当次窄门禁通过 | 不能借给重写期快照 |
| 历史 × 常规整书 | `knowledge-model=1`、overall failed | 当次常规整书门禁失败 | 不能被历史子绿抵销 |
| 历史 × 出版 release | `release_mode=false` | 未执行，不作通过判断 | 不能借常规模式结论 |
| 重写期快照 × capstone | 在第一处旧包哈希漂移处退出 2 | 对旧 manifest 失败关闭 | 不能借历史 capstone 绿 |
| 重写期快照 × 常规整书/出版 release | 没有形成新的最终报告 | 保持 Pending | 不能从契约单测外推出整书状态 |

这张四格表是一个很实用的会议工具。只要有人说“已经通过”，马上追问他指哪一格；只要有人说“现在
失败”，再追问是身份核验失败、规则违例，还是整书调度失败。很多争论并非技术结论不同，而是双方
各拿一格说话，却省略了行列标题。

项目经理于是退了一步：“那我只签第一句，再把候选包交给下一个人。”评审人仍没有落笔。第一句本身
可以作为历史事实，但若移交时不带输入身份与验证器身份，下一个人只拿到一个脱离对象的 0。第10章
刚刚拆过这种错误：PASS 不是可从关系上撕下来的贴纸，退出码 0 也不是。

### 11.1.2 同一文件名下面已经换了工作树

2026-08-14 的重写期诊断快照在所记录工作树运行 `capstone.py`。程序甚至没有走到 SHACL：

```text
[BUNDLE] FAIL: bundle input hash drift: ontology/abox-eps-decomposition.ttl
expected=0132155d8070f2c3168f82ea9bcc9eaf1bd14270aa5d802356c0b15c69594ff0
actual=4d03d0c6ea30965d868b67b4e7c52849808d45ba70232fa154576e17b720e952
exit code: 2
```

旧 manifest 仍在，开发目录里的分解 ABox 已经变化。程序拒绝把新字节塞进旧包，也没有借用历史绿灯
继续运行。有人把这叫“收口脚本坏了”，其实恰好相反：若它悄悄吸收当前文件，再沿用旧包 ID，才是
配置身份失守。

这次复跑还揭示了两个不能混在一起的快照。历史报告中的 `drift=[]` 只说明那次
`run_all_gates` 的前后两次发现集一致；它没有承诺 8 月 13 日以后仓库永远不变。重写期快照的 10 处
哈希漂移也没有推翻历史报告；它只说明该快照不是旧 manifest 声明的那一包字节。过去发生过什么，
后来在什么身份下重放，是两本账。

“那就把仓库切回旧提交再跑一遍”也只解决了一半问题。历史提交可以帮助重建当时的受控副本，却
不能授权把当前开发目录里尚未提交、但有意保留的章节重写与本体修订覆盖掉。重演历史应在隔离副本、
明确提交与依赖环境中进行；重写期工作树承担的是下一候选的开发事实。把开发目录回滚到旧提交，会把
“验证历史”偷换成“抹去开发变化”。因此本章保留旧清单、只读检查快照漂移，而不为了得到绿色演示去
覆盖开发工作树中有意保留的改动。

还要把观察、诊断与处置分成三层。观察是程序实际给出的字段和退出码；诊断是依据日志、代码和环境
解释它为何如此；处置是决定阻断接受、退回责任章还是形成新候选。历史 JSON 足以支持“常规整书红”这个
观察，却不足以恢复具体诊断；合取合同足以支持“当次不接受”这个处置，却不授权任何人猜出一条失败
原因。把 Unknown 留在诊断栏，不会削弱报告，反而阻止未经证据的故事混进历史记录。

### 11.1.3 先把待签主张写成能被反驳的句子

报告桌上真正待签的主张因此被改写为：

> 对一个明确标识的候选知识包，使用明确标识的验证器、查询、oracle、fixture 和运行环境，
> 当次检查得到所记录的子门禁与总门禁结果；未决项、模型覆盖边界与人类复核状态同时随报告移交。

这句话不承诺全绿，也不承诺产品安全。它只要求一次收口把四组关系钉在一起：验了什么输入，用什么
检查，得到了什么结果，还有什么未决。历史 JSON 已经有其中一部分，旧 manifest 也钉住了一部分；
两者仍没有自动组成重写期快照可签的结论。

评审人给这份报告开了四个 Hold。输入 Hold：明确历史包和重写期快照不能串用。检查器 Hold：bundle
哈希没有覆盖 `eval/`、正文和 oracle，必须另记验证器与整书发现集身份。结果 Hold：子绿不能覆盖总红，
诊断缺失不能靠猜。工程边界 Hold：三案例的结构深度、执行状态与专家复核必须分开报告。

这四个 Hold 不要求先“多跑一次”。若输入对象没说清，跑十次只会多十个无主语的结果。于是收口章
的第一刀不是查查询，而是回答一个第10章已经问过、现在扩大到整本书的问题：这次究竟验的是哪一包
字节？

## 11.2 这次究竟验的是哪一包字节？

团队最先提出的办法是打一个 Git 标签。仓库确实由 Git 管理，标签也能指向整棵目录树；但收口对象
不是“那时仓库里的一切”，而是一次显式选择。正文、习题、评审笔记、ABox、TBox、Shape 和验证
代码处在同一棵树里，只有其中一部分进入 capstone 数据包。Git 回答整树怎样演化，manifest 回答
这次具体让哪些字节承担被检查对象。二者可以互相引用，不能互相代替。

### 11.2.1 四十一个输入怎样成为一个可指称对象

历史 `bundle-manifest.yaml` 登记 41 个输入：40 个 `data` 和 1 个 `shapes`。每条只保留三个身份字段：

```yaml
schema_version: 1
bundle_id: ch11-capstone-three-items
generated_at_utc: '2026-08-13T07:29:28.530395+00:00'
bundle_sha256: bb175401749789024a28801a01dea8f31d2a2d1331a31535806857f032300912
inputs:
  - path: ontology/abox-eps-decomposition.ttl
    role: data
    sha256: 0132155d8070f2c3168f82ea9bcc9eaf1bd14270aa5d802356c0b15c69594ff0
```

`path` 必须是规范的仓库相对路径，不能有绝对路径、`..`、别名或两个路径指向同一解析位置；`role`
只有 `data` 与 `shapes`，且后者必须恰好一条；`sha256` 绑定文件字节。加载器还检查 schema、bundle
ID、输入存在性、哈希格式和重复项。任何已编码条件不满足，都以 `BundleManifestError` 失败关闭，
不会给缺字段猜默认值。

包级哈希不是把 YAML 文件直接再哈希一次。程序先把每条记录压成 `path/role/sha256` 三元组，按
路径和角色规范排序，再用键排序、无多余空格的确定性 JSON 序列化，最后取 SHA-256。这个步骤排除
了两种无关自由度：清单条目换序不应改变“包是什么”，YAML 缩进或引号换一种写法也不应改变数据包
身份。`generated_at_utc` 是生成元数据，不参加包级身份；只改时间戳，manifest 文件哈希会变，
`bundle_sha256` 不应变。

`bundle_id` 与摘要也要成对引用。ID 给人一个稳定的系列名称，摘要给某一组确切内容做区分；同一个
`ch11-capstone-three-items` 若配上不同 bundle 哈希，就是同系列的不同候选，不能仍称“同一包”。
反过来，只拿一长串摘要而不带 ID、用途和生成记录，虽然能精确比字节，却很难在评审中说明这串字节
承担什么角色。人类可读名称与机器摘要各守一半身份。

规范化选择的目的也不是让 manifest 本身不可变。条目换序、YAML 引号和生成时间可以改变清单文件
字节，却不改变被选择的数据包；因此 manifest 哈希会敏感，bundle 哈希故意不敏感。两个结果一变一不
变时，不应自动报警为矛盾，而应按各自对象解释：清单载体换了，规范化选择没换。只有报告预先声明
“manifest 文件本身也必须逐字相同”时，前者才是阻断条件。

这里同时出现三个哈希，职责各不相同：

| 身份 | 绑定对象 | 能回答的问题 | 不能回答的问题 |
|---|---|---|---|
| 单文件 `sha256` | 一条输入的字节 | 该文件是否仍是登记版本 | 内容是否正确、是否获批 |
| `bundle_sha256` | 规范化后的输入选择与各自字节哈希 | 两次数据包选择是否相同 | manifest 排版、验证代码与运行环境是否相同 |
| `manifest_sha256` | manifest 文件原始字节 | 清单文件本身是否变化 | 其中登记的工程结论是否充分 |

哈希很擅长识别“是不是同一字节”，不擅长判断“这字节值得信吗”。冻结动作是否经授权、上游是否
评审、oracle 是否正确、专家是否同意，仍在哈希之外。把哈希叫“内容审定证书”，只是给确定性算法
安排了它从未拥有的判断权。

四十一个输入也不是从目录里随手抓来的同类文件。它们包括三个案例的 ABox、共享 TBox、受控判定表
和方法表、来源锚以及一份 Shapes 图；有的提供项目事实，有的提供词汇与约束，有的只提供来源坐标。
`role=data` 只是 RDF 加载角色，不表示其中每一条三元组都是“项目实测数据”；`role=shapes` 也只是
指定本次 SHACL 约束图，不表示所有验收规则都住在这个文件里。查询文本、精确 oracle、fixture 和
Python 控制逻辑仍在 41 项之外，稍后必须另记身份。

因此 manifest 本身也要接受选择审查。漏掉一个已经被主张依赖的 ABox，会形成“包内自洽、包外缺件”
的假绿；多纳入一个尚未获准的草稿，则可能让临时事实改变查询结果。路径列表完整不完整，不能由
列表自己的哈希证明，就像装箱单上的封条不能证明仓库里没有漏装。清单回答“本次声称装了什么”，
来源覆盖、责任章交接与整书发现门禁分别帮助回答“本来应该装什么”。

### 11.2.2 十处漂移为什么不是十个该自动修好的错误

`capstone.py` 遇到第一处不符就停止，因此诊断运行只打印 `abox-eps-decomposition.ttl`。重写期快照
对 manifest 做了不修改文件的离线比对，共有 10 个登记输入与所记录工作树字节不同：

| 漂移组 | 当前不符的登记输入 | 变化意味着什么 |
|---|---|---|
| 分解知识 | `abox-eps-decomposition.ttl`、`asil-decomposition-schemas.ttl` | 第8章对象或允许方案已演化 |
| 共享语义与门禁 | `fsafety-tbox.ttl`、`shapes.shacl.ttl` | 类、属性或校验合同可能变化 |
| 来源坐标 | Part 1/2/7/8/9/10 的 source-anchor 文件 | 来源覆盖与坐标登记已演化 |

表里没有判定这些变化是好是坏。它们可能是前面各章重写后经过审查的修订，也可能包含尚未收束的
工作树变化；哈希比较只报告“不再相同”。正因为 TBox、Shapes 与来源锚也在漂移，自动重算 manifest
尤其危险：它会把“开发目录现在恰好是什么”改写成“收口决定接受什么”，中间跳过责任章审查、影响
分析与集成判定。

数字 10 来自一次离线全表哈希核对；`capstone.py` 的失败签名只有第一项，不是它已经依次诊断了十项。
这种 fail-fast 设计适合保护旧包：第一处身份不符已经足以否定“当前字节就是旧候选”，继续解析只会
扩大一个无效运行的噪声。离线盘点则服务影响分析，可以一次列全漂移，但它没有替每项变化作接受判定。

四个小变式能把身份层次校准得更准：

1. 只调换 `inputs` 的书写顺序，规范化排序后的 `bundle_sha256` 应保持不变，manifest 原始字节哈希会变；
2. 只改 `generated_at_utc`，包身份仍不变，manifest 文件身份会变；
3. 把同一路径从 `data` 改成 `shapes`，选择语义变了，包哈希也必须变，而且“恰好一个 Shapes”合同
   可能立即失败；
4. 只改输入内容却只更新条目哈希、不更新包级哈希，加载器应因包摘要不一致拒绝；若两级哈希都更新，
   那就不是“修好旧清单”，而是形成了一个必须重新评审的新候选。

这四个变式共同说明：哈希不是越多越好，而是每一层都要有清楚主语。若两个摘要对同一变化给出不同
反应，先问它们绑定的对象是否不同，不要急着把其中一个判为“算法错误”。

合理的反对意见是：“既然我们就是要验当前工作树，为什么不先刷新清单再跑？”因为刷新是一项状态
改变，不是诊断动作。它生成新的候选对象，旧报告不再适用；而当前全书重写尚在进行，哪些上游修订
可以进入下一包还没有统一裁决。此刻最诚实的结果就是失败关闭，并保留旧 manifest 作为历史冻结
身份。等责任章修订收束、适用门禁完成、受控集成允许以后，才显式生成新清单。

### 11.2.3 初始快照与末次复核夹住的是什么

即使 41 个哈希在开始时都一致，运行仍有一个时间问题。若程序先逐项检查磁盘文件，随后又按路径
重新解析，某文件可能在两次读取之间变化：核验的是 A，进入图的却是 B。当前实现因此把每条输入
一次读成字节快照，先比哈希，再直接从已核验字节解析 RDF 与 Shapes。末尾重新加载 manifest 与
全部输入，检查包身份和 manifest 文件哈希仍与开始相同。

这套机制给出一个窄而重要的结论：查询与 SHACL 消费的是开始时已核验的字节，不会静默吸收后来
版本；若末次观测到持续漂移，本次运行作废。它也有明确盲区：文件若在两次观测之间变化又恢复，
末次复核未必看见该事件。不过实际解析仍使用初始快照，不会吸收那段瞬时内容。把这条盲区写在报告
里，比把“两次一致”夸成“整个运行期间绝无变化”更有工程价值。

把运行拆成四个时刻更容易看清这一点。`t0` 读取 manifest 并记住它的原始哈希；`t1` 逐项读取
文件 A，核对其登记哈希并把已核验字节留在内存；`t2` 从内存中的 A 构图、查询和校验；`t3`
重新读取磁盘与 manifest，确认可观察到的末态仍对应 A。若磁盘在 `t1` 后变成 B，解析不会吸收 B；
若到 `t3` 仍为 B，末次复核会让运行失败；若中途 A→B→A，末态检查看不见事件，但执行对象仍是
内存快照 A。这个合同防的是“验 A、算 B”的检查时/使用时错位，不是宣称拥有文件系统的连续监控。

若项目确实要求证明整个窗口内没有任何写入，仅靠双端哈希不够，还需只读介质、不可变对象存储、
受控锁或可审计文件事件等更强机制。本书没有悄悄借用这些条件，所以报告只写“初始快照被消费，末次
观测一致”，不写“运行期间绝无修改”。把保护强度说准，本身就是收口质量的一部分。

> 图 11-1（占位）：冻结与收口是两个动作。责任章先修订、审查和受控集成，`freeze_bundle.py` 才显式生成清单；`capstone.py` 只读核验初始字节快照、从该快照解析、运行查询与 SHACL、再做末次复核。任一已观测漂移都失败关闭；缺口退回责任章，不能在收口现场补数据后沿用旧身份。

### 11.2.4 冻结者与收口者不能在同一步偷换角色

本章目录里两个脚本的分工很刻意。`freeze_bundle.py` 计算当前选择的输入哈希并写出新 manifest；
它只做字节登记，不判断输入是否已经专家批准。`capstone.py` 只读加载既有 manifest，运行已登记检查，
不会因发现缺口去写 ABox，也不会自动调用冻结工具。一个负责形成候选快照，一个负责检查候选快照。

若把两者串成“发现漂移→自动重冻→继续验收”，失败关闭就被改造成静默追随。程序永远能得到一份
与当时磁盘一致的清单，却再也回答不了“谁决定这些变化可以进入本次候选”。所以重写期快照的十处
漂移没有触发任何重冻；它们作为输入 Hold 原样留在桌上。

整个候选生命周期可以写成五个互不偷换的动词：开发表示文件仍可演化；集成表示责任边界已经接受
一组变化共同进入候选；冻结表示选择与字节获得 manifest 身份；检查表示指定验证器对该身份产生当次
结果；接受表示有权限的主体综合结果、未决与边界作决定。工具可以自动完成冻结与检查中的机械部分，
不能把“检查绿”直接改写成“接受”，更不能从开发态跨过集成直接冻结。

五个动词也解释为什么旧 manifest 不该跟着工作树走。它记录的是一次已经发生的冻结，不是一个指向
“最新文件”的动态书签。动态书签适合开发者导航，不适合给历史报告作主语；报告需要能在半年后仍
回答当时选中了什么，即使后来的目录已经完全不同。

输入对象终于说清了。可是 manifest 里的 EPS、BMS、AEB 都能被列为 `data`，并不表示三个相关项
在包里拥有同样深的生命周期结构。路径同在一张清单上，只解决“是否入包”，没有解决“入包的是什么”。

## 11.3 三个案例都进了包，为什么不能写“同样成熟”？

项目经理看到 manifest 同时列出 `abox-eps.ttl`、`abox-bms.ttl` 和 `abox-aeb.ttl`，又提出第二个
看似自然的摘要：“三个相关项已经统一装载并通过同一套规则。”前半句可以在某个有效冻结运行里成立，
后半句仍需拆开。统一工具链没有抹平输入深度，正如三名学生在同一考场不表示答了同样多的题。

### 11.3.1 同载、可查、工程充分是三种不同强度

先拿 EPS 的 `ECU_SPFM` 走三格。第一格是同载：包含该对象的硬件 ABox 能与其他已登记输入一起被
RDF 解析，并接受同一 TBox 与 Shapes。它只证明当前加载路径没有因该对象失败。第二格是可查：查询
能返回 `appliesToElement`、`achievedPercent`、项目目标和 `forSafetyGoal` 等关系，数值比较 Shape
也能在当前图上执行。这说明已编码字段可以对账。第三格才是工程充分：99.4% 是否来自受控 FMEDA，
失效率与诊断覆盖是否可信，分配边界是否合理，结果是否经授权评审并足以支持产品主张。

本书只把 `ECU_SPFM` 放到前两格。它显式标为 `TeachingExample` 和 `EvidenceCandidate`，数值与理由
都是教学输入，不来自真实 FMEDA。同载是可查的前提，可查可以为充分性评审组织材料；任何一格都
不能跳过中间条件冒充后一格。

这组三分法也解释了历史报告的限制。那份 JSON 记录 capstone 返回 0，却没有保存三案例查询的逐行
输出；我们可以签“子进程返回 0”，不能仅凭总退出码重建它当时打印了哪些 Item、计数和标签。当前
`eval/eval-cases.yaml` 又登记了精确 oracle，但旧 manifest 已漂移；截至重写期诊断快照，尚未形成
可把两者重新绑定的新冻结运行。验收合同存在，不等于验收已经执行。

把例子换成 BMS 的 `TSR_CellVoltageMonitor`，三格仍然成立。它可以与共享图同载，可以沿
`derivedFrom` 找回对应 FSR 与安全目标，也可以证明当前窄 GATE 看见了一个已分配系统层后代；但这
不等于监控器的软件实现已经编码、硬件采样链已经分析、阈值已经标定或集成试验已经执行。模型中的
一条分配边只声明“当前候选把责任指向这里”，不携带实现完成证书。

同载与可查属于知识表示的运行事实，工程充分属于对象世界的判断。前者可以由解析器、查询和 Shape
给出确定性结果；后者要消费 FMEDA、试验、评审、供应商证据和项目授权。把两类语言分开不是降低
本体的价值，反而让它发挥合适的作用：把该交给人的材料组织到位，把尚未拥有的证据槽空着，而不是
用一条看似完整的 RDF 路径把空槽涂绿。

### 11.3.2 同一清单里的三种深度

不运行查询，manifest 的路径选择本身已经能回答一个较弱但可靠的问题：每个案例有哪些生命周期
ABox 入包。按层摊开，差异很明显：

| 已登记层次 | EPS | BMS | AEB |
|---|---|---|---|
| 概念与 FSC | 概念 ABox + FSC 候选 | 概念 ABox | 概念 ABox |
| 系统需求与架构 | 系统、集成、Clause 8 确认候选 | 一条 FSR→TSR 的最小系统链 | 一条 FSR→TSR 的最小系统链 |
| 硬件度量 | 有教学 SPFM/LFM 对象 | 未登记对应 ABox | 未登记对应 ABox |
| 软件需求与单元 | 有 SSR、软件单元和计划态验证 | 未登记对应 ABox | 未登记对应 ABox |
| 分解与 DFA | 有分解候选，DFA 仍待执行 | 未登记对应 ABox | 未登记对应 ABox |
| 生产运行 | 有定义态特殊特性、控制步骤和现场过程 | 未登记对应 ABox | 未登记对应 ABox |
| 支撑过程 | 有两项工具 usage 教学评估 | 未登记对应 ABox | 未登记对应 ABox |
| 安全档案 | 有开放 Claim、Argument 与候选证据角色 | 未登记对应 ABox | 未登记对应 ABox |

空格只表示这一版候选包没有登记相应 ABox，不表示真实世界一定没有工作。反过来，EPS 那些“有”也
只表示对象存在；其中大量状态仍是 Draft、Planned、NotRun、NotPerformed、Candidate 或 Open。
结构深、对象多和活动完成是三条不同轴线。

BMS 与 AEB 的最小链不是劣质填充物。它们让同一 TBox、分配 Shape、ASIL 继承和跨案例查询在独立
命名空间上复用，并故意把软件、硬件、分解与生产空档留在明处。若只留下结构最深的 EPS，读者很
容易把“查询能走到底”误解成工具天生保证全生命周期；短链迫使报告区分“没有命中条件”和“尚未
建模到那一层”。

一个更诚实的三案例状态卡，应当至少并列三根轴。第一根是结构覆盖：候选包实际登记到哪些生命周期
层、哪些关系可查。第二根是活动状态：已建对象分别是 Draft、Planned、NotRun、Performed 还是
Accepted。第三根是证据充分性：状态声明有没有来源、执行记录、独立评审和授权支撑。EPS 在第一轴
比 BMS/AEB 长，不代表第二轴走得更远，更不代表第三轴已经成立。

以“有软件层”为例，三根轴会写出完全不同的话。结构轴可以说 EPS 登记了 SSR 与 SoftwareUnit；
状态轴接着说相关验证仍为计划态或未运行；充分性轴再说没有真实软件项目、覆盖结果与批准记录。
若只保留第一句，读者会自然脑补后两句；收口报告的任务恰恰是阻止这种脑补。

RDF 的开放世界语义又给空格加了一层边界：图里没写 BMS 的软件对象，不等于现实世界断言“BMS
不存在软件”。本章能说的是“该 manifest 锁定的候选包未登记对应 ABox，当前查询在该层无结果”。
若验收合同要求某层必须存在，需要另写闭世界范围、激活条件和缺失即失败的门禁；不能因为 SPARQL
返回空，就把知识库的沉默翻译成产品事实。相反，门禁对明确范围内的缺项给出红灯时，也只是说明
合同所需断言未在当前图中成立，后续仍要由责任章判断是漏建、范围错还是工程活动未开始。

### 11.3.3 两张计数表为什么不能互相代抄

当前机器资产里有两种看似相近的三案例查询。`capstone.py` 的展示查询对每个 Item 统计危害事件、
安全目标以及 FSR/TSR/SSR/HSI 四类派生需求；它用于运行时鸟瞰，没有在脚本内给出精确 oracle。
`CQ-CH11-01` 则只数已分配到元素的 FSR 与 TSR，并把当前教学回归基线锁为 AEB=2、BMS=2、
EPS=6。一个问“当前图显示多少已登记派生需求”，一个问“当前教学基线有多少已分配系统层需求”；
把前一个输出抄进后一个 oracle，会把不同问题伪装成同一计数。

`CQ-CH11-02` 又问第三件事：哪些 Item 经危害事件归属路径拥有 ASIL D 安全目标。当前 oracle 精确
绑定 AEB 的 `SG_NoUnintendedBraking` 与 EPS 的 `SG_NoUnintendedAssist`；BMS 不在结果中，因为
当前教学图的最高目标为 ASIL C，不是因为 BMS “没做 HARA”。精确绑定保护的是这组受控教学数据的
回归，不是规范规定“一定要有两个 D 级目标”。上游数据受控改变时，oracle 也必须作为同一变更接受
审查，不能让测试把旧世界强压回去。

`CQ-CH11-02` 的 Item 归属也不是靠 URI 里有没有 `eps`、`bms` 或 `aeb` 字符串判断。查询从 Item
走到它拥有的 HazardousEvent，再沿 `leadsToSafetyGoal` 找 ASIL D 目标。若错误地把命名空间当所有权，
一个跨域引用或复制改名就可能把别案目标算到当前 Item 名下；沿显式关系走，至少能让这类污染成为
可检查的图事实。命名习惯方便人读，不能承担工程归属。

计数更不能替状态投票。EPS 的层次最深，仍可同时拥有 Planned 的测试、NotRun 的集成活动、
NotPerformed 的 DFA 和 Open 的 Claim；BMS/AEB 链短，却可以诚实地让现有 FSR/TSR 在窄合同下通过。
“有八层”不是 80% 完成，“只有两层”也不是 20% 完成。层次描述模型宽度，状态描述已登记活动位置，
充分性还要由各自证据判断；报告若只留一个百分比，会把三根轴压成一个无法复核的分数。

还要把机器合同自己的治理状态写出来：`CQ-CH11-01/02/03` 与 `GATE-CH11-01` 当前四项
`expert_review_status` 全部为 `pending`。精确 oracle 和契约测试可以先作为开发回归使用，却不能
冒充专家已经接受这些能力问题、范围与预期世界。规则也有“可运行”与“已审定”两本账。

### 11.3.4 只加一个文件，成熟度仍不会自动前进

做一个单因变式。假设明天有人在工作树新建 `abox-bms-hardware.ttl`，里面有完整 Turtle 语法和一组
教学度量。只改变这一事实，旧 manifest 仍没有点名它，历史包身份也不变；capstone 不会自动发现该
文件，报告仍只能说旧包未登记 BMS 硬件层。若重新冻结把它纳入，新包也只多了一组候选结构；其来源、
数值理由、Shape、反例和责任章审查没有因此自动完成。

把这个文件送到可接受结论，至少要过七扇不同的门：

| 门 | 可观察的关闭证据 | 仍没有获得什么 |
|---|---|---|
| 文件存在 | 规范路径上有明确字节 | 语法、语义与入包资格 |
| 单文件可解析 | Turtle 解析成功 | 与共享 TBox/其他案例相容 |
| 责任章接纳 | ch06 核对对象、数值、理由、来源和教学状态 | 收口包身份 |
| 受控集成 | 共享类、引用对象、查询与 Shape 影响已审查 | 新 manifest |
| 显式冻结 | 新候选点名文件并生成新摘要 | 门禁通过 |
| 检查通过 | 指定验证器对新身份得到记录结果 | 工程内容充分与授权接受 |
| 人类接受 | 有权限角色依据真实证据作有限决定 | 超出决定边界的产品结论 |

七扇门不是要求七个部门盖章，而是七种主语不能合并。实际流程可以把相邻动作安排在一次评审里，但
报告仍要能区分“解析器接受了语法”“责任章接受了事实”“评审人接受了候选”。否则一句“已接入”会
在不同人口中分别指存在、入包、绿灯和放行，下一次变更就无人知道该重开哪一层。

这就是“同样成熟”摘要的断口：文件存在、清单入包、解析同载、查询可达、门禁通过、工程充分与
授权结论，是一串相邻却不相等的事件。下一步不再横看三案例，而是选 EPS 最深的一条链纵向钻进去。
若连这条链都不能说清闭到哪里，三案例的总括性结论更无从谈起。

## 11.4 一条追溯链到底闭到了哪里？

评审人没有接受“EPS 已覆盖到软件层”这句话。他随手点了一条危害事件：
`HE_UnintendedAssist_Highway`。“从这里讲到软件单元。不要打开一张导出的全景图，逐跳说主语、类型
和关系；哪一跳只是候选，也当场说出来。”

这道题把前十章压回一条线。若回答者只能报出文件名，说明资产虽多，关系还没进入他的判断；若能
把链念完，又把“可达”说成“已实现”，则是另一种越界。

### 11.4.1 六个节点怎样穿过四个责任章

当前 EPS 教学图登记了下面这条软件主链：

```sparql
PREFIX iso262: <https://w3id.org/iso26262#>
PREFIX eps:    <https://w3id.org/iso26262/eps#>
SELECT ?fsr ?tsr ?ssr ?unit WHERE {
  eps:HE_UnintendedAssist_Highway iso262:leadsToSafetyGoal ?sg .
  ?fsr a iso262:FunctionalSafetyRequirement ; iso262:derivedFrom ?sg .
  ?tsr a iso262:TechnicalSafetyRequirement  ; iso262:derivedFrom ?fsr .
  ?ssr a iso262:SoftwareSafetyRequirement   ; iso262:derivedFrom ?tsr ;
       iso262:allocatedTo ?unit .
  ?unit a iso262:SoftwareUnit .
} ORDER BY ?ssr
```

第一个节点是第4章的危害事件，它以 `leadsToSafetyGoal` 指向
`SG_NoUnintendedAssist`。第二跳到第5章的 `FSR_DetectUnintendedAssist`，第三跳到
`TSR_TorquePlausibility`。第7章再从这条 TSR 派生两条 SSR：
`SSR_InputPlausibility` 分配给 `SWU_PlausibilityCheck`，`SSR_TorqueRangeCheck` 分配给
`SWU_TorqueMonitor`。危害事件、目标、FSR、TSR、SSR、软件单元六类节点因而可以被同一条闭跳
查询串起。

逐跳念关系并非仪式。`derivedFrom` 的主语是下游需求、宾语是它所承接的上游对象；`allocatedTo`
的主语仍是需求，宾语才是承担它的元素。若把方向记反，一张箭头方向随意的汇报图可能看不出问题，
SPARQL 会直接少行。若把 `allocatedTo` 错写成元素指向需求，肉眼仍觉得“两者连上了”，责任落点
门禁却不会承认。关系名、方向和类型一起构成可执行语义，少一项都只能算视觉邻近。

“闭跳”不是说工程闭环，而是查询逐层点名类型、每次只走一步。若有人让 SSR 直接从安全目标派生，
一个宽泛的 `derivedFrom+` 仍会认为上下游可达；上面的查询会因为中间缺 TSR 而少结果。层级审计
需要这种敏感性。

反过来，GATE-CH11-01 只想问“范围内目标是否至少存在一个已分配的安全需求后代”，就使用
`derivedFrom+` 和 `rdfs:subClassOf*`。它不关心将来中间多一层合法需求，因而对层级扩展更稳健。
两条查询沿同一关系行走，却故意对不同变化敏感。查询与需求一样，必须先说明什么变化应当打破它。

这条闭跳查询当前返回两条 SSR 行，也不能被改写成“SG1 的全部软件需求只有两条”。它只枚举满足
这组类型、方向和分配条件的路径：未装入候选包的对象、使用另一条合法关系表达的支路、没有分配的
草稿 SSR 都不会出现。查询结果的全称范围来自 `WHERE`，不来自读者对列名的想象。要证明“全部”，
还需先定义总体与发现边界，再用缺口查询验证没有遗漏；一个正向列表天然更擅长证明存在，不擅长证明
不存在第三条。

这里可以看出两种常见的追溯假绿。第一种是路径压缩：用 `derivedFrom+` 证明上下游可达，却漏掉
强制中间层；第二种是节点点名：报告列出 SG、FSR、TSR、SSR 和单元五个名字，却没有验证它们按
正确方向相连。闭跳查询专门对付前者，关系模式对付后者；它们仍没有阅读需求文本，也没有证明两个
软件单元真正实现了相应行为。

### 11.4.2 主链之外还有四条异构支路

若把追溯只画成一根软件链，前几章的交接仍会被压扁。`SG_NoUnintendedAssist` 周围至少还有四类
不同端点：

| 支路 | 当前已登记对象 | 它把主链接到哪里 | 当前边界 |
|---|---|---|---|
| 硬件度量 | ECU 的 SPFM/LFM、助力电机的 SPFM 教学达成 | 通过 `forSafetyGoal` 回到 SG1 | 数值不是 FMEDA 结果，元素达标不推出整项达标 |
| 分解岔口 | C(D)+A(D) 两条分解需求与 `Decomp_DetectAssist` | 从 FSR 分出主通道与监控通道 | DFA 与充分独立仍为待执行/待判断 |
| HSI 支线 | `HSI_TorqueSignal`、`HSI_TorqueDiagnosticUse` | 从 TSR 落到软硬件接口需求与责任元素 | 规格仍为 Draft，诊断覆盖率、响应参数和集成验证尚未完成 |
| 生产延长线 | 转矩标定、软件版本两个特殊特性及序号 10/20 的控制步骤 | 从 HSI/SSR 走到生产定义 | 只有定义态结构，没有批准的执行与放行记录 |

四条支路没有强行使用同一种端点。硬件侧把达成值、目标值、元素和安全目标分开建模；分解侧保存
合法组合、括号标记和证据槽位；HSI 把接口规格与其中的接口需求分开；生产侧区分特殊特性、控制步骤
定义和未来执行记录。追溯的目的不是
让所有对象长得一样，而是让不同形态仍能回答“它为何出现在这条主张附近”。

这也给“链闭合”三个不同含义。图论可达只问有没有路径；结构完整按查询合同检查预期类型与关系；
工程闭环还要判断需求内容、实现、执行、证据和授权。正文后面凡说“闭”，都必须带上是哪一种。

支路还提醒我们，追溯不是一条万能的 `relatedTo`。`derivedFrom` 回答“这条要求承接谁”，
`allocatedTo` 回答“谁承担它”，`forSafetyGoal` 回答“度量服务于哪个目标”，Safety Case 的证据边
回答“论证准备消费什么”，生产步骤的顺序又回答“定义态流程怎样排列”。把它们都压成“相关”，
全景图会更简洁，能力问题却全丢了：你再也分不清一项度量究竟是从目标派生，还是仅用于支持该目标；
也分不清一个工作产物是证据候选，还是实现责任落点。

因此跨章总装不是统一成一种边，而是在共享身份上保留多种关系的语法。`SG_NoUnintendedAssist`
之所以能成为主轴，不是所有文件都指向它，而是各支路以适合自己的关系与它建立可追问的连接。总图
若只剩一团线，收口要做的第一件事不是加颜色，而是恢复每条边所回答的问题。

### 11.4.3 同一查询移到 BMS 与 AEB，空结果应怎样归因

BMS 的主链在 `TSR_CellVoltageMonitor` 停下，AEB 在 `TSR_CrossCheckTargets` 停下。两条 TSR 都
已经分配到元素，两个 SG1 也都显式带 `hasSystemDevelopment true`，所以它们在当前
GATE-CH11-01 范围内，并由现有 FSR/TSR 后代满足“至少一个已分配安全需求后代”的窄合同。它们
没有 SSR 和软件单元；把 11.4.1 的闭跳查询换成对应命名空间，会在 SSR 那一跳返回空。

范围标记在这里很关键。BMS 的 `SG_PreventOvercharge` 与 AEB 的
`SG_NoUnintendedBraking` 都显式声明 `hasSystemDevelopment true`，所以窄 GATE 要检查它们；
各自现有的已分配 FSR/TSR 足以满足“至少一个后代”的条件。两案的次要目标
`SG_NoFalseShutdown` 与 `SG_DetectAndBrake` 没有该标记，当前不进入这条 GATE。未激活不是通过，
而是这条查询不作判断；若项目决定它们也进入系统开发，必须先受控改变范围事实，再接受新增门禁结果。

这个空不是门禁失败，也不是查询语法错误。manifest 的层次对照已经登记“BMS/AEB 软件层未建”，
所以当前最有根据的归因是模型到此为止。若未来明明有软件 ABox、同一查询在 EPS 也突然全空，才应
优先怀疑查询或数据。空结果没有自带原因，原因来自查询合同、已知正例、范围清单和责任记录的共同
比对。

### 11.4.4 只改一条分配事实，哪一种“闭”先断？

现在做一个单因变式：不删危害事件、目标、FSR 或 TSR，只把某个已进入系统层的非 QM 安全目标
派生树上全部 `allocatedTo` 边移除。闭跳查询仍可能把危害事件一路查到 SSR，因为派生关系没断；
但 GATE-CH11-01 的违例查询会返回该安全目标——它要求至少一个后代既属于安全需求子类闭包，又有
分配对象。

这次碰撞说明“能沿 `derivedFrom` 走通”不等于“已有责任落点”。恢复分配边以后，存在性违例消失，
仍不能推出每条需求都已分配、分配内容正确或责任方接受。一个门禁应该拒绝它声明要拒绝的错误，
也应允许合同之外的未知留给其他检查；把所有问题塞进一个 `TraceCompleteShape`，只会制造一盏没人
知道为何变红的总灯。

把三项合同并列成一个小真值表，射程会更清楚：

| 图中状态 | 直接 FSR Shape | 后代分配 GATE | EPS 闭跳查询 |
|---|---|---|---|
| 有直接 FSR、有已分配 TSR、没有 SSR | 绿 | 绿 | 在 SSR 跳为空 |
| 有直接 FSR、有派生树、全部后代未分配 | 绿 | 红 | 可能仍能列出路径 |
| 跳过直接 FSR，直接造已分配 TSR | 红 | 可能绿 | 因强制 FSR 跳而空 |
| EPS 完整教学软件主链 | 绿 | 绿 | 返回当前两条 SSR 路径 |

“可能绿”不是漏洞，而是提醒我们该项合同从未宣称检查那件事。好的门禁组合像几把口径不同的卡尺：
每把有自己的被测尺寸和误差边界。把它们的绿灯做逻辑与，可以扩大已检查的条件集合；仍不能从有限
卡尺推出整件产品没有未建模缺陷。

链的结构说清以后，项目经理抓住了另一个看似更强的事实：“既然安全目标附近已经挂了七件候选证据，
总能把 Claim 关掉吧？”追溯把对象送到论证桌上，恰好不能替论证桌作结论。

## 11.5 七件候选证据为什么仍关不上一个 Claim？

第3章已经在 `abox-eps-safetycase.ttl` 中建立 `Claim_SG1` 与 `Arg_SG1`。第4至第8章的对象陆续被
接到论证下；最近一次受控修订又让 Clause 8 的安全确认规范草稿与报告模板成为候选证据。到收口时，
论证一共指向七件材料。

错误的数数法是：五件时没关，七件总该更接近关闭。证据角色不是投票人，Claim 也没有“候选件超过
六份即通过”的票数规则。每件材料支持哪一段推理、处于什么状态、缺什么活动，要逐件读。

安全档案里至少有三种不同句法。Claim 写“我们准备主张什么”；Argument 写“为什么这些材料合在
一起能够支持该主张”；Evidence 写“哪件可定位材料承载哪一段事实”。只有文件名而没有论证桥，七件
材料只是七个附件；只有漂亮 Argument 而没有足够证据，则只是推理提纲；Claim 的状态又必须由适用的
评审与授权动作推进，不能由附件计数器推进。三者互相需要，却没有任何一者能代替另外两者。

本书把这些对象标为 `EvidenceCandidate`，用意正是把“已被论证指向”与“已被接受为充分证据”拆开。
候选状态允许团队提前发现证据槽、版本与来源断口；若一开始非得等所有活动完成才建立 Safety Case，
收口只会在最后一天第一次看见缺件。提前建骨架是增量治理，提前宣告骨架已经承重则是越界。

### 11.5.1 七件材料分别允许说到哪里

| 候选证据角色 | 来自哪里 | 当前可以支持的窄叙述 | 仍不能支持什么 |
|---|---|---|---|
| `HARA_Report_Draft` | ch04 | SG1 的教学风险路径已登记 | HARA 已获项目批准 |
| `FSR_DetectUnintendedAssist` | ch05 | SG1 有一条功能需求后代 | 需求内容充分、已实现 |
| `TSR_TorquePlausibility` | ch05/ch10 | 技术需求与后续对象可追溯 | v1.8 现实评审或验证完成 |
| `ECU_SPFM` | ch06 | 教学度量对象与目标关系可查 | 真实 FMEDA 与整项度量达成 |
| `Decomp_DetectAssist` | ch08 | 分解候选的结构条件已登记 | DFA 已执行、独立性已证明 |
| 安全确认规范草稿 | ch05 Clause 8 | 确认对象、环境、方法和判据有候选结构 | 规范已批准、用例已执行 |
| 安全确认报告模板 | ch05 Clause 8 | 未来报告与结果/评价的接口已登记 | 报告已有真实结果或接受结论 |

七件对象都带 `EvidenceCandidate`。`Arg_SG1` 可以引用它们，说明当前论证准备消费什么；引用不会
把 Draft 变 Approved，也不会把教学值变成工程结果。安全档案的作用是组织主张、论证和证据，不是
用一条 `backedByEvidence` 边制造事实。

逐件读还有一个好处：它暴露证据不是可互换筹码。HARA 草稿帮助解释目标从何而来，却不能证明软件
实现；SPFM 教学对象回答硬件度量结构，却不能证明 Clause 8 安全确认已经执行；安全确认报告模板
规定未来结果放在哪里，却没有任何当次结果。少一份所需类别的证据，不能用三份别类附件补票。证据
数量只在“有没有重复或遗漏”这类库存问题上有意义，论证充分性看的是支持关系与内容。

这里还要纠正责任归因。这两件 Clause 8 候选角色不是收口脚本临场写进 Safety Case 的。它们先由
第3章 CAE 责任边界接纳、审查并进入上游 ABox，ch11 只读消费。若收口章一边检查上游、一边为让
图好看而补候选证据，manifest 的只读承诺就被自己破坏了。

### 11.5.2 一条状态链比七个文件名更诚实

`CQ-CH11-03` 不数材料，而是把 Clause 8 对象和 Claim 的状态一次绑定出来：

```text
Specification: review=Draft, evidence=EvidenceCandidate
Activity:      execution=SafetyValidationPlanned
Result:        status=ValidationCaseNotRun
Evaluation:    status=ValidationEvaluationNotPerformed
Report:        review=Draft, evidence=EvidenceCandidate
Claim:         status=ClaimOpen
```

六行没有矛盾。规范和报告可以在 Draft 时作为候选证据角色；活动可以已经计划而未执行；结果对象可以
先建成 `NotRun`，评价对象也可以先建成 `NotPerformed`；开放主张可以提前收集这些边界。真正的错误
是把对象存在翻译成活动发生，把模板存在翻译成结果通过。

当前 `capstone.py` 会把这条链打印成边界视图，但有一个容易被多读的实现细节：若查询没有命中，
`clause8_boundary()` 只打印“未命中”提示，本身不改变 capstone 退出码。精确状态是否仍与合同一致，
由 `CQ-CH11-03` 的 exact-bindings oracle 和契约测试承担。展示函数、验收查询和程序总判定是三个
层次；看到屏幕上有一段漂亮状态输出，不能反推这段输出已被 capstone 总退出码逐字段把守。

六个状态也不是一根共同进度条。规范的 review status、活动的 execution status、结果和评价的
存在/执行状态、报告的 review status、Claim 的开放状态分别属于不同对象。把它们排成六行，是为了
看跨对象是否讲得通，不是说后一行只能在前一行“100%”后才存在。报告模板可以在活动前建立，Claim
可以从项目早期保持 Open，评价对象也可以先以 NotPerformed 占位；诚实的占位比空白更可审计。

做两个对照就能看出状态不能串改。若只把报告模板从 Draft 改为 Approved，而活动仍 Planned、结果
仍 NotRun，最多说明模板评审前进了，不能把 Claim 关掉。若安全确认已经执行并产生结果，但评价仍
NotPerformed，则“有测试输出”也不能自动变成“结果满足接受准则”。状态升级必须落在实际发生的
对象上；把一个对象的成熟标签借给邻居，是 Safety Case 最隐蔽的假绿之一。

### 11.5.3 安全档案可以增量生长，里程碑不能被随便改写

ISO 26262-10:2018 §5.3.2 是资料性指南中的解释框架，不是本章另造一组规范性 shall。它说明安全
档案可以作为增量活动，与安全生命周期其余开发阶段集成；其中的 Note 说安全计划可以纳入增量步骤
和初步版本的策划。正文随后给出三个示例里程碑：技术安全需求验证后可形成 preliminary version，
系统设计验证后可形成 interim version，最终功能安全评估报告之前可形成 final version。

这三个时间点很具体。把第一个示例改写成“概念阶段结束”是一种常见误读，会把指南举例的演进节奏
前移；这里按物理页 23 的结构化提取块保留原有顺序。指南还说明安全档案接受 ISO 26262-2:2018 §6.4.9 所给的确认
评审；相关项发生修改时，要评价对安全档案的影响，并在必要时结合修改更新。资料性解释可以帮助
安排中间版本，不能代替 Part 2 的适用要求、项目计划或真实评审。

因此，候选知识包可以被当成一种教学中间版本，却不能仅因“增量”二字把未执行活动提前记功。增量
意味着主张与证据随生命周期生长，正好要求每个版本保留 Draft/Planned/Open 的诚实状态；它不是
允许最终结论分期预支。

三个示例里程碑还说明，中间版本的名字不是成熟度荣誉。在这组资料性示例中，preliminary version
出现在 TSR 验证之后，interim version 出现在系统设计验证之后，final version 临近最终功能安全评估
报告。ISO 并没有借这三个例子硬性定义所有项目的版本名；本书为避免进度错觉，采用的报告纪律是：
若更早建立 Safety Case 骨架，就明确称草稿或计划中的初步材料，并同时写出实际进入条件，不借用一个
听起来更成熟的名称代替状态。版本语义应由当时可消费的对象和评审目的说明，不由文件名独自承担。

修改后的义务同样重要。安全目标、架构、工具版本或适用假设变化时，不是只替换一份附件，而要问
哪条 Claim、哪段 Argument、哪些证据角色与确认评审受影响。增量 Safety Case 的优势在于影响关系
可追，不在于每次修改都能局部无痛吸收；必要时旧版本必须保持历史有效范围，新版本重新开放相应主张。

### 11.5.4 多加一件候选证据，Claim 仍不会自动投票通过

再改一个事实：给 `Arg_SG1` 多挂一份工具资格计划，候选证据从七件变八件，其余状态不变。Claim
仍应是 Open。工具计划没有执行，且即使工具真的完成资格，也只增强对特定工具输出的置信，不能
代偿安全确认 `NotRun`、DFA 待执行或 HARA 未批准。

反方向也成立：若未来某件证据被接受，Claim 是否可以升级仍取决于完整论证、其他必要证据、确认
评审、发现处置和授权主体。状态跃迁需要证据与治理动作，不由 SPARQL 的 `COUNT` 触发。

真正有用的收口问题因此不是“有几件”，而是四连问：这件材料支持哪条子主张；它的内容与版本是否
明确；它当前是候选、已评审还是已接受；尚缺的动作由谁在什么条件下关闭。四问里任何一问答不上来，
增加附件数量只会扩大未决清单。机器可以检查角色、状态与精确绑定，论证作者和确认评审人仍要阅读
内容、挑战推理并承担接受决定。

项目经理终于不再数材料，转而质疑机器本身：“你反复说门禁很窄。它到底真会咬，还是只会在好数据
上打印绿灯？”这必须用反例回答，不能再靠边界声明自证谦虚。

## 11.6 一处单因错误，门禁究竟会不会精确咬住？

最差的反例是把一份图改坏十处，运行后得到二十条红灯，再宣布“系统很敏感”。这种结果无法说明
哪条规则发现了哪个错误，也无法知道修复一处后为什么仍红。第4章建立的纪律在收口章继续有效：一次
只改一个与合同同型的事实，事先写出预期 focus、Shape 或查询结果，再观察实际签名。

这套做法有三个角色。缺陷模型先说现实里担心哪种坏法，例如“目标已有派生需求，但没有任何责任
落点”；单因变异把这句话翻成一处最小图差异；oracle 再声明程序应当报告哪个 focus、多少结果和
什么退出语义。没有缺陷模型，变异只是随机破坏；没有单因差异，失败无法归因；没有精确 oracle，
任何红灯都能被事后解释成成功。

反例也不是对正本“试试看”。它是一项测试资产，必须能在完整临时副本中注入、观察和恢复，不给
历史 manifest、共享工作树或报告留下未声明变化。越接近收口，越不能用破坏候选本身来证明门禁会
保护候选。

### 11.6.1 两条都谈追溯的合同，射程并不相同

本章附近有两项常被混为一谈的检查：

| 合同 | 激活与问题 | 合格条件 | 单因错误的预期签名 |
|---|---|---|---|
| `SafetyGoalHasFSRShape` | 进入系统层的目标是否有直接 FSR | 至少一条直接 FSR | 删除目标的全部直接 FSR，命中该 Shape |
| `GATE-CH11-01` | 进入系统层的非 QM 目标是否有已分配安全需求后代 | 至少一个经 `derivedFrom+` 可达、带 `allocatedTo`、类型属于安全需求闭包的后代 | 保留派生树但删除全部分配边，违例查询返回该目标 |

第一条保护层级入口，第二条保护至少一个责任落点。某目标可能有直接 FSR，却没有任何后代被分配：
第一条过、第二条红。也可能有一条已分配 TSR，却因错误建模跳过直接 FSR：第二条可能过、第一条红。
这不是规则互相打架，而是两个不同问题没有被一盏总灯压平。

读一条门禁时，可以固定问三句话。激活域是谁：哪些目标会被检查，哪些因为范围或状态不在本合同内；
义务是什么：直接一跳、任意后代、至少一个还是全部；失败签名是什么：Shape 结果、SPARQL focus、
退出码还是仅有展示提示。很多“测试明明过了却没抓住问题”的争论，实际是把激活域外对象、合同外
义务或非判定型输出误当成同一件事。

### 11.6.2 一个已执行的契约测试怎样推翻绿灯

`eval/test_capstone_bundle.py` 里有一个最小图：一条 ASIL D 安全目标已标记进入系统层，派生树上有
安全需求并带分配。基线运行 `trace_gaps()` 返回空。测试随后只移除所有 `allocatedTo` 三元组，
其余类型、ASIL 和 `derivedFrom` 不动；预期该目标出现在缺口列表。另一个测试再加一层防伪：普通
非需求节点即使有 `derivedFrom` 和 `allocatedTo`，也不能满足门禁，因为它的类型不在
`SafetyRequirement` 子类闭包。

重写期诊断快照执行这组 capstone 契约测试，24 项全部通过。它们还覆盖 data/shapes 哈希漂移、路径逃逸、
manifest 身份篡改、初始快照、末次复核、查询文本一致性、Clause 8 精确状态、标签回退和三案例
oracle。这里能签的只是“这些 24 个已编码契约在当前测试环境中按预期工作”，不是完整候选包通过；
旧 manifest 的 10 处漂移仍使同一快照的 capstone 运行在装载前失败。

旧稿曾给出书旁测试入口；该入口已随唯一执行语义迁移而撤销。现在只能从
ontology-engineering skill 根调用统一入口；它逐项核验 source lock 并自动注入
Semantica runtime identity，调用者不得手抄。binding 与 task 按
[`semantic-engagement-contract.md`](../../semantic-engagement-contract.md) 建立：

```bash
runtime/.venv/bin/python scripts/semantic_engagement.py discover
runtime/.venv/bin/python scripts/semantic_engagement.py run \
  --binding /path/to/package-binding.json \
  --task /path/to/task-envelope.json \
  --scenario semantica.vol2.ch20.scenario.primary
```

命令执行的是 Semantica 声明的 ch20 场景，不会重冻历史 manifest。场景结果与独立
release verdict 必须分开；当前 package 为 `partial`、release `blocked`。原生
`semantica package ...` 只供底层 runner/manifest 诊断，不是主运行路径。

把 24 项按故障族而不是按文件顺序读，更容易看见覆盖边界。身份族挑战路径、哈希、角色和包摘要；
快照族挑战核验后磁盘变化；语义族挑战 trace 查询、类型闭包与三案例精确结果；报告边界族挑战标签
回退、Clause 8 状态和失败关闭。四族都通过，只说明这些已命名坏法被当前测试捕获。它们没有枚举
RDF、SPARQL、SHACL 或工程建模的所有可能错误，也没有证明测试代码本身不存在共同模式错误。

直接 FSR 的 Shape 还有一份注册 fixture：它在 EPS 概念与系统上下文中移除
`FSR_LimitAssistTorque` 和 `FSR_DetectUnintendedAssist` 作为主语或宾语的全部三元组，期望
`SafetyGoalHasFSRShape` 恰好报告 1 个结果。这个精确数量是当前上下文的回归合同；若将来另一个
Shape 也因同一变异报警，fixture 应失败并要求重新审查规则交互，而不是把额外红灯一律当成“更安全”。

“恰好 1”守的是诊断可解释性，不是追求越少越好。若新增的一条规则按设计也应对该缺陷报警，应先
更新故障模型，说明两个结果各自保护什么，再受控改 oracle；若额外结果来自无关 Shape，则它暴露
约束耦合或 fixture 污染。直接把期望改成“至少 1”，回归会继续绿，却把以后所有意外连锁报警藏掉。
反例资产与生产规则一样需要版本和评审，不能为了适配新输出随手放宽。

### 11.6.3 从基线、变异到恢复，三次运行各证明什么

一个合格的故障演练有三步。基线先证明临时副本与预期良态一致；变异运行证明单因错误触发预期合同；
恢复运行证明去掉该差异后签名回到基线。只跑中间一步，无法排除副本原本就红；只看出现任意红灯，
无法排除命中的是另一个错误。

这三步都必须在完整临时工作区副本中进行。manifest 点名的数据变化会触发哈希漂移；未入 manifest
的 `eval/` 查询、oracle 或 fixture 变化又会改变检查含义而不改变 bundle 哈希。只复制一份 TTL，
却继续从共享正本运行脚本，不是真正隔离。实验报告至少记录基线身份、注入差异、预期签名、实际
签名和恢复结果。

完整副本还有一个常被忽略的理由：正本可能同时处于有意的脏工作树状态。若实验只复制数据，却从
正本加载查询和 TBox，基线已经不是 manifest 对应的完整组合；若测试失败，无法知道是注入差异还是
共享依赖变化。可靠流程应在副本里先证明基线，保存差异补丁或三元组清单，再执行一个变异，最后
恢复并重算关键哈希。恢复失败本身就是测试失败，不能把“反例已命中”当作结束条件。

故障演练也要有停止条件。基线不绿就不注入；变异除了预期文件还改动其他对象就作废；实际签名与
预期不同就保留诊断而不继续叠加第二个变异；恢复后身份或结果不回到基线，就销毁临时副本并调查。
这些条件把“试一试”变成可复核实验，也保护团队不从一堆互相污染的红灯里挑自己喜欢的解释。

### 11.6.4 红灯也有不能证明的事

门禁精确抓住“没有已分配后代”，不等于它知道为何没有。可能是责任章漏建分配，可能是目标错误地
进入系统层，也可能是当前范围定义变化。机器先报告 focus node 与合同断口，人再回到版本、来源和
责任记录归因。反例证明规则对一种已声明缺陷有感，不证明未注册的所有坏法都能被发现。

列几种仍可从窄门禁旁边经过的坏法：需求文本与目标语义不一致，但关系边齐全；分配到了一个类型
正确却能力不合适的元素；目标本应进入系统开发，却漏写 `hasSystemDevelopment`，导致门禁根本未
激活；一条已分配后代存在，其他关键后代全部悬空；或所有教学结构都正确，现实工程活动仍未执行。
它们需要内容评审、范围完整性检查、更强的全称门禁或真实工程证据，不能要求一条存在性查询包办。

所以规则覆盖表至少应登记“已捕获的缺陷模型、激活域、正例、单因反例、预期签名、已知盲区”。
盲区不是羞耻栏，而是下一个评审人判断该不该新增规则的入口。没有边界声明的强规则最危险，因为
报告读者会把它没说的话也当成承诺。

至此，绿灯和红灯都有了有限含义。可复现结论还差最后一层：另一个人必须使用同一数据、同一检查器、
同一 oracle 与足够接近的运行语义，才能判断两次结果是否真的相同。只给他一份 bundle，仍然不够。

## 11.7 怎样让别人复现的是同一个结论，而不只是同一份数据？

团队把旧 manifest、历史 JSON 和重写期诊断快照的 capstone 输出摆成三列。一个工程师说：“数据包
哈希已经有了，验证器不过是一段确定性代码，没必要再登记。”评审人把快照中的 `capstone_sha256` 与历史报告的
逐文件清单比了一遍：两者恰好相同，都是
`9dabae7f4a669d40b6e0a3fad7964b0a2cdae88f8052305fffcfdf1452121d9b`。这次相同是可用证据，
不是“代码天然不变”的证明。若没有两边的哈希，谁也无从知道。

更有意思的是，快照记录的运行库版本也与历史报告一致：CPython 3.13.12、RDFLib 7.6.0、pySHACL
0.40.1、PyYAML 6.0.3。验证器与主要运行库没换，程序却在装载前失败；快照中可定位差异集中在
manifest 输入与工作树字节不一致。这个对照比一句“环境应该一样”强，因为它把已观察到的同与异
分别落了字段；它仍不排除报告未登记的操作系统、文件系统或底层库差异。

“复现”在这里也要分档。原字节、原验证器和足够相同的运行语义再次得到相同观察，是重放；换一台
受控环境、仍能得到约定等价结果，是更强的可复现性主张；数据或验证器已经改变后重新运行，则叫
重新评价，不应继续声称重放旧结论。三者都可能有工程价值，最忌讳的是把第三种挂在第一种的报告号下。

结果相同也不自动证明过程等价。两次都返回 0，可能一次实际运行了全部查询，另一次因为条件分支
跳过了半数；两次都返回 1，也可能命中完全不同的 focus。可比对象至少是“身份＋已执行检查集＋精确
结果/诊断”，不只是最后一个整数。

### 11.7.1 一次结论至少需要四层身份

收口结果的主语不是一个文件，而是一次组合：

| 层 | 至少登记什么 | 为什么不能省 |
|---|---|---|
| 被检查数据 | bundle ID、单文件哈希、`bundle_sha256`、`manifest_sha256` | 固定数据选择、字节与清单文件 |
| 检查器合同 | `capstone.py`、`run_eval.py`、CQ/oracle、fixture 注册与数据、Shapes 的哈希 | 同一数据交给不同规则可能得出不同结论 |
| 运行语义 | Python、RDFLib、pySHACL、PyYAML 版本及关键选项 | 解析、RDFS 推理与 SHACL 行为可能随版本或配置改变 |
| 当次观察 | 起止时刻、退出码、逐门禁结果、诊断、耗时、未决项与边界 | 身份相同也仍要记录实际发生了什么 |

四层可以压成一张结果指纹卡，却不宜压成一个不可解释的总摘要。数据指纹变化，说明被测对象变了；
检查器指纹变化，说明问题或 oracle 变了；运行语义变化，说明同一代码的执行解释可能变了；前三层
都相同而观察不同，才优先调查非确定性、外部状态或记录缺失。分层身份让差异诊断有顺序，而一个总
哈希只能告诉你“某处不同”。

运行环境也不该无限登记。CPU 序列号、桌面主题通常与 RDF 结果无关；Python 与 RDFLib 版本、推理
模式、SHACL 选项、区域设置、并行调度和影响路径解析的文件系统语义则可能相关。选择原则是：凡可能
改变输入发现、解析、查询、约束或结果排序的因素，应进入报告或可追溯环境锁；其余保留在运行平台
记录里。所谓“足够接近”，必须由预先说明的等价条件支撑，不能由操作者凭感觉判定。

历史 `run_all_gates` 报告在更外层发现了 540 个可影响验收的输入，前后
`input_manifest_sha256` 都是
`0610e25cc8bf2d515687cf6b6bb0924d4ef1428efe31d9d59ada41ed63e9bec9`。逐文件清单包含
`run_all_gates.py`、`run_eval.py`、`eval-cases.yaml`、`shape-fixtures.yaml`、capstone 脚本、数据和
正文。因此它比 41 输入的 bundle 更接近“这次整书验收用的是什么”。它仍没有自动保存每个子进程
的完整 stdout；身份覆盖广，不等于诊断内容完整。

这里没有一个“万能总哈希”。bundle 哈希故意排除检查器，使数据候选可以被多个检查器消费；全量
输入 manifest 又把检查器和报告相关文件纳入，识别一次更宽的验收运行。两个层次各自有用。若为了
省事只留最外层哈希，读者很难单独比较数据包是否没变；只留 bundle 哈希，又无法知道规则是否已换。

### 11.7.2 capstone 与整书门禁为什么必须并排而不是二选一

`capstone.py` 与 `run_all_gates.py` 看起来都能给出最终退出码，职责却不同：

| 入口 | 主要对象 | 它特有的保护 | 它不能代替的东西 |
|---|---|---|---|
| `capstone.py` | manifest 锁定的 41 输入候选包 | 初始字节快照、包级身份、末次复核、三案例展示与窄 trace 检查 | `eval/`、正文与全部 CQ/fixture 的版本化验收 |
| `run_eval.py` | 当前开发态登记的数据、CQ/GATE、Shapes 与 fixture | 元门禁、精确 oracle、主图 SHACL、正负 fixture | 冻结包字节身份与末次 manifest 复核 |
| `run_all_gates.py` | 一次整书验收发现集及各子门禁 | 前后全量输入发现/哈希、逐门禁退出码、JSON 汇总 | 子门禁未输出到 JSON 的内部诊断与专家判断 |

三者形成的是外层调度下分层、部分重叠的合同，不是三个平级投票箱，也不是彼此逐层调用。
`run_all_gates` 调度并记录子门禁；`capstone` 与调用 `run_eval.py` 的 `knowledge-model` 是两个兄弟
GateSpec：前者对显式冻结包承担身份和窄总装检查，后者展开开发态知识模型的精确 oracle 与 fixture。
外层可以把两个退出码纳入合取，却不会因此继承子进程没有输出的逐行诊断；任一兄弟子合同通过，也
不会知道正文、图计划或其他发布资产是否满足外层合同。

runner 还可能按顺序遇首红即停。因此“没有某项结果”要区分未计划、显式跳过、因前项失败未启动、
超时中止和已运行但报告漏记。历史报告的九个 `gates` 条目恰好都在，最后一项红；将来的报告不能只
看 `full_run` 猜执行覆盖，而要逐项记录状态。未运行不是绿，也不是红，它是需要保留原因的第三种状态。

因此历史报告中“capstone=0、knowledge-model=1、总状态 failed”不是两套工具意见不合。capstone 只
说明旧冻结包在它的窄合同下通过；常规整书门禁检查更宽的开发与验收合同，其中至少一项失败。总报告按
合取语义裁决：必要子门禁有一个红，不能用另一个绿抵销。

这些旧 runner 名称只用于解释历史报告的分层语义，今天不再是可调用入口。读者复核
迁移后的候选绑定时，唯一入口是：

```bash
runtime/.venv/bin/python scripts/semantic_engagement.py discover
runtime/.venv/bin/python scripts/semantic_engagement.py run \
  --binding /path/to/package-binding.json \
  --task /path/to/task-envelope.json \
  --scenario semantica.vol2.ch20.scenario.primary
runtime/.venv/bin/python scripts/semantic_engagement.py verify \
  --binding /path/to/package-binding.json \
  --task /path/to/task-envelope.json \
  --scenario semantica.vol2.ch20.scenario.primary
```

历史快照中旧 manifest 漂移、旧 capstone 返回 2 仍是可以保留的历史事实；它现在由
Semantica ch20 的 `legacy-capstone-*` 资产登记，不能通过重建被删脚本来复现。验证报告
必须同时写 package、scenario、source commit、wheel SHA-256、输入/输出哈希与 receipt。
统一入口自动绑定前两类 source identity；原生 `semantica package ...` 仍只供底层诊断。

历史整书 runner 默认曾在首个失败处停止；当时的诊断运行可带 `--keep-going` 收集同一
工作树上的更多结果，并把该调度选项写进历史报告。该 runner 与参数现已撤销，不能调用或
恢复；这段记录只说明过去的调度差异从未把红灯变绿，也未替代输入快照和必要门禁的合取裁决。

### 11.7.3 前十章的形态怎样在同一份报告里再被触发

收口不是把十章目录复制进附录。每章建立的一种结构，只有在同一候选包里被查询、Shape 或状态视图
再次消费，才算真的接上总装：

第2章的概念网提供共享类、属性与术语边界；第3章提供确认措施目录、治理状态和 CAE 人机边界；
第4章的有限判定表让 S/E/C→ASIL 与受控 oracle 对账；第5章的 `derivedFrom/allocatedTo` 形成本章
走过的主链；第6章把达成值、目标值、元素和理由拆开；第7章把方法表变成受控行与单元；第8章把
分解例外写成白名单、括号标记与证据槽；第9章区分生产定义、执行和现场闭环；第10章再把工具、
usage、版本和复用通道接回同一快照。

这些不是九张相互独立的成绩单。判定表形态在第8章的分解方案和第10章的 TCL Table 3 重新出现；
追溯链长到软件、分解、HSI 与生产特殊特性；CAE 又把跨章对象收在开放 Claim 下。复用发生在关系
上，不发生在章节标题上。

> 图 11-3（占位）：两个前置构件、六个映射形态与第10章跨部复用汇入候选知识包。收口运行让相应查询、Shape 或状态视图再次触发；“触发”只是检查执行，不表示原工程活动完成。书稿层 `EPS-S11` 汇集 `GOV-S03`、`EPS-S09` 与 `SUP-S10`，不表示 EPS 产品生命周期自动推进。

总装图的价值不是证明“全书都覆盖了”，而是暴露没有消费端的承诺。某章若声称建立一种可复用模式，
收口时却找不到查询、Shape、状态视图或报告字段，那个承诺仍停在讲解层。反过来，存在一个消费端也
不证明模式足够一般；BMS/AEB 的最小链只说明当前共享模式能接住这两个受控教学样本。

可以把六种形态的消费方式再摊开。有限判定表由精确输入输出 oracle 消费；追溯链由路径查询与缺口
门禁消费；数值表由值、目标、范围与理由的 Shape 消费；方法矩阵由行、适用等级和推荐强度的转录
检查消费；例外表由允许组合、括号标记和反例消费；状态机则由合法状态、对象分层和不可跳跃的精确
绑定消费。它们共享“把隐含裁量摊成有限合同”的骨架，却没有被硬塞进一种数据结构。

第10章的复用再增加一个维度：同一工具材料能否跨 usage、版本或产品通道重用，要回到输入假设、
版本身份和 impact analysis，而不是因为文件哈希相同就自动继承接受。收口消费这种形态时，检查的是
复用主张是否带足条件，不是替现实项目批准复用。这样回读前十章，读者看到的不是章节摘要，而是每种
方法在总装端究竟长出了哪颗牙。

### 11.7.4 四要素报告怎样避免把总红写成局部绿

一份最小可复核报告至少按以下顺序写：输入与检查器身份、当次结果、未决项、边界声明。顺序不是
排版偏好。先写身份，读者才知道结果属于谁；结果之后立即列未决，局部绿不会把欠账挤到附录；最后
把机器射程写进结论，防止转述时只剩“通过”。

把历史报告改写成一段合格的窄摘要，可以这样写：

```text
对象：input_manifest_sha256=0610…bec9 的历史整书发现集；
      其中 capstone 使用当次 manifest 锁定的数据包。
检查：各子门禁及运行库版本见逐文件清单和 runtime 字段。
结果：capstone-three-items rc=0；knowledge-model rc=1；overall=failed。
未决：JSON 未保留 knowledge-model 的内部失败签名；专家复核与产品工程判断不在此报告内。
边界：以上是书稿知识模型检查记录，不是 ISO 26262 验证、确认措施或产品放行。
```

这段话没有把历史红灯修好，却让另一个人知道该到哪里继续查。可复核报告的价值不只在全绿时出现；
红灯若绑定对象、检查器和诊断，也是可移交的工程结果。

历史报告暴露的改进点也很具体：以后至少要为每个子门禁保存有界诊断摘要，包含首个失败合同、focus
或异常类别、完整日志位置与哈希；既不能把数万行 stdout 全塞进总 JSON，也不能只留退出码。总报告
负责导航，子日志负责复盘，两者用稳定 ID 和哈希相连。日志若因权限或保留期不可用，报告应把诊断
状态写成 Unknown，而不是让后来的人用当前失败猜历史失败。

红报告同样需要不可变保存。若团队只归档最终绿版，前一版的未决、漂移和处置因果会消失，下一次
同型失败只能重新调查。失败不是待删除的草稿，而是说明某一候选为何没有被接受的工程记录；它的
效力边界比成功报告更需要写清。

### 11.7.5 只换验证器，旧绿灯为何必须重议

做最后一个单因变式：41 个数据输入和 bundle 哈希完全不变，只把 GATE-CH11-01 从“至少一个已分配
后代”改成“每条安全需求后代都必须分配”，或者把 CQ-CH11-03 的 exact bindings 放宽成 row count。
数据没变，检查问题和允许的世界已经变了。旧 capstone 退出码不能直接搬到新合同下。

若新旧验证器都返回 0，也只能说各自在自己的合同下通过；不能因为颜色相同就认为结论等价。验证器
哈希、查询文本、oracle 与 fixture 身份之所以必须进入报告，正是为了让“检查什么”不藏在一个绿色
图标后面。

验证器变化可以再分三类。纯重构若有证据证明语义等价，仍需登记新身份并跑等价回归；扩大义务会让
原绿候选重新接受更强问题，旧绿只能作历史基线；放宽 oracle 则改变允许世界，必须解释为何不是为了
迁就当前数据。把三类都写成“脚本更新”会丢掉最重要的影响方向。数据配置管理与验证器配置管理必须
并行，谁也不能躲在另一个的哈希后面。

现在，待签报告已经有了输入、检查器、运行语义、结果和边界。还剩一个治理问题：检查发现 BMS 缺
硬件层、AEB 缺软件层，或者 Safety Case 少一件候选证据时，谁有权动正本？收口人若顺手修，刚建立
的对象与检查器分离会立即倒塌。

## 11.8 收口发现缺口，谁有权修改什么？

最危险的“积极”发生在验收现场。一个查询为空，收口工程师知道大概该补哪条边，于是在 ABox 里加
一行；Shape 变绿以后，他更新 manifest，继续跑完，纪要写“发现并关闭一处缺口”。技术上动作很快，
治理上却把被检查对象、检查者和冻结者合成了一个角色。谁审查新增事实、它来自哪一章、旧报告为何
还能引用，全都消失。

本章的默认动作只有三个：只读定位，登记缺口，退回责任章。修订由责任章接纳和审查，经受控集成后
形成新候选，再显式冻结并重跑。慢的不是工具，而是保留“谁决定了什么”的因果链。

把角色拆开看，至少有五顶帽子：事实责任人维护上游工程对象；规则责任人维护能力问题、oracle 与
fixture；集成人确认多章对象能否共同进入候选；冻结者按获准选择生成 manifest；收口评审人只读消费
候选并作有限裁决。小团队里同一个人可以戴多顶帽子，但不能把五个动作压成一次未记录的提交；每次
换帽子都要留下输入、理由和复核人。角色分离的目标不是制造组织图，而是避免检查者在看见红灯后
悄悄改题、改答案、重封包，再以同一身份宣告通过。

缺口也不是一条“请修复”消息。最小缺口单应包含：观察到的 focus 或空结果、被检查包与验证器身份、
期望合同、当前事实、已知来源、影响的能力问题、责任边界、建议关闭证据和禁止的临场补丁。这样责任
章接到的是一个可重放问题，不是总装端的猜测；修订回来后，ch11 也能检查它关闭的是原缺口，而非只
让某条输出消失。

### 11.8.1 重写期十处漂移为什么必须保持为可见 Hold

诊断快照中的 10 处漂移发生在全书重写期间，包含分解、共享 TBox、Shapes 和来源锚。它们并非 ch11 可以
批量吸收的“新版本”。分解对象要回第8章确认；共享 TBox 与 Shapes 需要受控集成；来源锚要回各自
责任章核对正文实际消费与坐标。只有这些上游裁决完成，冻结工具才有权把它们组成下一版 manifest。

旧 manifest 此时有双重价值。第一，它保存一个历史候选的精确输入身份，让旧报告仍有主语。第二，
它作为重写期工作树的比较基线，准确暴露哪些输入已经离开那一版。若为了让教程命令跑通而刷新，它的
两种价值会同时丢失。

Hold 也不是对十处变化作负面技术评价。它只说在责任、影响与集成决定完成之前，这些字节不能借旧
候选身份进入收口。某项修订后来可能全部被接受，也可能被拆分、回退或改由另一版本消费；在决定前
统一保持 Hold，能避免“看起来只是来源锚”或“看起来只是 Shape”这种文件名直觉抢走审查。共享 TBox
的一行变化可能影响三案例，来源锚的一行变化可能改变覆盖声称，表面大小都不是接受依据。

同理，旧 manifest 失败关闭不表示其中登记的历史字节已经“不正确”。它只是拒绝把快照字节冒充成
历史字节。内容评价与身份评价是两套问题：前者问修改是否更好、更真、更完整，后者只问是不是那一版。
收口先把后者钉死，责任章才有一个稳定基线去讨论前者。

### 11.8.2 缺口不是按发现地点分工，而是按事实责任分工

| 收口发现 | 应退回的责任边界 | ch11 可以做什么 | ch11 不可以做什么 |
|---|---|---|---|
| BMS 缺硬件度量/分析片段 | ch06 或明确的 BMS 硬件副线 | 登记缺口、定义未来接入检查 | 编造 SPFM/LFM 数值或假装 FMEDA 已完成 |
| AEB 缺 SSR、软件单元和方法选择 | ch07 或 AEB 软件副线 | 说明当前链止于 TSR | 临场补 SSR 让端到端查询有结果 |
| BMS/AEB 缺分解、DFA 或生产闭环 | ch08/ch09 | 记录范围与接入判据 | 用 EPS 对象复制改名冒充新案例证据 |
| 工具、DIA 或复用路线缺口 | ch10 | 把缺口接到共同快照问题 | 用工具材料代偿产品验证 |
| Safety Case 候选角色或状态问题 | ch03 CAE 治理边界及对象责任章 | 只读消费已接纳的论证结构 | 直接把 Claim 或 Evidence 状态升级 |
| 查询、oracle、fixture 或收口报告缺口 | ch11/评估基础设施责任边界 | 修订检查合同并记录版本影响 | 修改上游事实来迎合旧 oracle |

“在哪发现”与“谁负责修”经常不是同一处。ch11 能看见跨章断口，正因为它站在总装端；总装端的视野
不自动带来上游事实所有权。若新事实同时影响多章，应该形成一份带消费版本、标识符、来源、能力问题、
反例和影响范围的集成请求，由具名责任人串行裁决。

这里的“串行”不是要求所有工程工作只能一个人做，而是要求同一候选的裁决顺序可追：事实先由责任
边界接纳，规则影响随后审查，集成决定再选择版本，冻结最后生成身份。硬件、软件和来源核对当然可以
并行准备；在它们尚未汇成一个明确决定前，不能让自动冻结抢先把某一瞬间的工作树变成候选。并行提高
准备速度，串行保存接受因果。

有些缺口确实属于 ch11 自己，例如查询把方向写反、exact oracle 锁错集合、报告漏存诊断。这时也
不能修改上游 ABox 来迎合旧检查，而应修改检查器合同、增加正反例并说明旧结果为何需要重议。总装章
拥有检查问题，不拥有被检查的工程事实；这条界线同时保护两边。

### 11.8.3 一次正确接入怎样走完整循环

假设 BMS 硬件团队最终形成 `abox-bms-hardware.ttl`。第一步不是放进 manifest，而是让 ch06 责任
边界确认它表达的对象、数值、目标、理由和教学状态；来源与权利账同步，适用 Shape 和单因反例进入
回归。第二步是集成检查：它引用的 BMS 元素、安全目标与共享类是否与当前 TBox 一致，是否碰到既有
查询和 oracle。第三步才是冻结：新文件被显式点名，所有受影响输入得到新哈希与新包 ID。第四步由
ch11 只读消费，更新三案例对照和未决项；若门禁红，继续登记并退回，不在收口现场第二次修。

四步之间各有一个可见出口。责任章不接受，变化停在开发态；集成发现冲突，形成影响分析而不冻结；
冻结后身份核验失败，候选作废而不自动重算；门禁运行红，报告保留 failed 并退回。任何出口都允许
项目继续学习，却不允许沿用旧 accepted 语气。失败关闭不是把工作锁死，而是阻止未经裁决的状态跃迁。

这个循环也适用于更小的变化。只改一条标签可能影响展示而不影响查询基数；只改一个 `hasASIL` 会
影响精确 oracle；只换一个来源锚会影响覆盖与坐标门禁。影响大小由关系决定，不由文件行数决定。

反过来，一个大文件的排版重流若规范化语义、来源坐标和输出都不变，影响可能很窄；一行
`hasSystemDevelopment true` 却会把一个新安全目标送进系统层 GATE。版本评审若只看“改了几行”，
会把真正高风险的语义开关藏在小 diff 里。收口端应按被触发的查询、Shape、证据角色和报告字段组织
影响分析，而不是按文件大小排优先级。

### 11.8.4 `EPS-S11` 只是书稿接口记号

全书调度表把 `GOV-S03`、`EPS-S09` 与 `SUP-S10` 汇入 `EPS-S11`。这个字符串帮助章节说明自己消费
哪些上游候选、产出怎样的书稿状态；当前 RDF 中没有一个 `EPS-S11` 实体，它也不是配置库冻结记录、
EPS 工程成熟度、产品版本或认证状态。

所以“到达 EPS-S11”最宽只能理解为：书稿已经为某一候选知识包定义收口问题、可执行检查、报告
边界和未决项接口。若某次诊断仍有 manifest 漂移、必要门禁为红或专家复核未完成，实际候选就不能写成已接受。
章节状态机走到书末，不等于产品生命周期走到终点。

责任终于落回各自边界。秘书把纪要最后一栏留给评审人：历史报告、重写期诊断快照和未来候选，各自能签
哪一句？这一次不能再用“基本完成”或“待完善”收尾，必须把主语、版本、结果与未决项写全。

## 11.9 回到放行桌，最终能签下哪一句话？

评审人把最初那句“capstone 绿了，先把第11章签掉”划掉。桌上其实有三个对象：一次历史整书运行，
一个已经漂移的旧 manifest 与重写期诊断快照，以及未来尚未形成的新冻结候选。把三者混写，任何一句
结论都会超宽；分开以后，裁决并不复杂。

### 11.9.1 对历史报告，可以签事实记录，不能签常规整书接受

历史报告允许签下：在 `input_manifest_sha256=0610…bec9` 标识的那次发现集上，前后快照未报告漂移，
capstone 子门禁返回 0，knowledge-model 返回 1，总状态为 failed。主要运行库版本与逐文件输入清单
已记录。由于 JSON 没有保存 knowledge-model 的 stdout，仅凭该报告不能确认具体失败签名；需要回查
同期日志或把原因记为 Unknown。

这份裁决既没有否定 capstone 绿灯，也没有让它覆盖总红。它保留一条窄历史事实，并明确诊断缺口。
最不能签的是“历史候选已通过全书验收”或“失败只来自无关章节”；报告字段都不支持这两句。

### 11.9.2 对重写期诊断快照，可以签失败关闭与契约测试，不能签候选包结果

快照可以签两条并列事实。第一，旧 manifest 的 41 个输入中有 10 个与所记录字节不符，capstone 在
第一处 `abox-eps-decomposition.ttl` 漂移处退出 2；程序没有静默重冻或吸收新字节。第二，该诊断快照记录
`eval.test_capstone_bundle` 的 24 项契约测试通过，包括哈希、路径、快照、查询一致性、Clause 8
状态与单因分配变异。

两条事实不能合成“该快照候选包通过”。契约测试证明检查器的已编码局部行为，capstone 则明确拒绝了
该输入身份。最诚实的快照状态是：检查器局部合同可运行，历史包无法在已演化工作树上重放，下一版
冻结尚未授权形成。

### 11.9.3 未来真正可签的收口句子长什么样

上游收束以后，新候选报告至少要能填满下面这张主张卡：

| 坐标 | 报告必须给出的内容 |
|---|---|
| 对象 | bundle ID、bundle/manifest 哈希、逐输入清单 |
| 检查器 | runner、capstone、run_eval、查询/oracle/fixture/Shapes 的身份 |
| 环境 | 主要运行库版本、推理与 SHACL 选项、并行条件 |
| 结果 | 每个必要子门禁的退出码、关键精确结果与诊断，不只给总色块 |
| 未决 | Drift、NotRun/NotPerformed/Open、模型空档、专家与权利状态、责任人与关闭条件 |
| 边界 | 明说知识模型检查不等于产品验证、确认措施、评估、批准或放行 |

主张卡可以在评审前先改成六个必填空：对谁——候选对象身份；谁来问——验证器合同；在什么语义下——
环境与选项；实际看见什么——结果与诊断；还欠什么——未决和责任人；这句话效力到哪里——边界。任何
一格写“同上”或“详见系统”，都要能沿稳定引用回到精确记录；否则报告只是把缺失信息搬到另一个
找不到的地方。

状态动词也应各安其位。Observed 表示记录到一个事实，Verified 表示指定验证活动对指定对象得到结果，
Passed 表示某一合同的接受准则满足，Accepted 表示有权限的角色接受候选，Released 则还包含适用发布
流程。它们不是可由机器自动递增的一列徽章：门禁 Passed 可以与产品工程 Not assessed 同时存在；
候选 Accepted 也不等于正式出版 release 模式已经运行。报告若只写“通过”，就把五种主语折叠了。

只有这些坐标都能回读，评审人才能写类似下面的窄句子：

> 对清单 X 锁定的教学候选包，验证器集合 Y 在环境 Z 中完成当次运行；报告所列机器合同得到结果 R，
> 未决项 U 保持开放。该结论只覆盖已登记知识结构与已编码检查，不构成三案例的工程充分性、
> ISO 26262 合规或产品放行。

若 R 中仍有红灯，整体状态就是 failed；窄的子绿可以分别记录，不能用“除个别问题外通过”擦掉
必要门禁。若所有机器门禁都绿，专家、来源、权利和真实工程状态仍按自己的账继续，不能被总绿吞并。

一份全红或半红报告并非没有结论。它可以明确拒绝哪一个候选、保留哪些局部成功、把哪些诊断退给
何种责任边界，并规定下一候选必须重新执行哪些检查。真正无用的是没有对象身份的“失败了”和没有
未决边界的“差不多通过”。收口质量不由绿色面积衡量，而由下一位评审人能否据此重复观察、理解断口
并避免误用旧结论衡量。

### 11.9.4 同一份报告走完九站，身上多了什么

回看这份待签报告的旅程。第一站，它只有一个诱人的 capstone=0；总红逼我们把子结论和发布主张
分开。第二站，旧 manifest 把对象钉成 41 个输入，重写期十处漂移又证明历史包与工作树不能混用。
第三站，三案例同在清单却深度不同，同载、可查和工程充分被拆成三格。第四站，EPS 主链从危害事件
走到软件单元，BMS/AEB 在 TSR 停下；路径可达、分配存在和工程闭环分开记账。第五站，七件候选证据
进入开放 Claim，Clause 8 仍停在 Draft/Planned/NotRun/NotPerformed。第六站，单因删除分配边让
窄门禁真正咬住，直接 FSR Shape 与后代存在性 GATE 各守一段。第七站，bundle、验证器、运行库和
当次结果组成可复现主语，六种本体化形态在同一报告里被再次消费。第八站，缺口退回责任章，收口
不修改上游。第九站，历史事实、当前失败关闭和未来候选句子各归各位。

这九站不是九份清单，而是同一个主张逐步变窄。第4章的 HE1 在七站中不断获得边界、等级、目标与
策略；本章的报告也在九站中不断获得对象、检查器、结果、责任和效力边界。写作上的复用因此对应
工程上的复用：不是把相同小标题复制一遍，而是让一个对象被连续问题改造，上一站产物成为下一站
不能跳过的输入。

### 11.9.5 思考与动手题

1. 历史报告中 `capstone=0`、`knowledge-model=1`、`status=failed`。分别写出三句不越界的事实，
   再写一句最容易误签的总括性结论，并指出它偷换了哪个验收对象。
2. 只改 manifest 的 `generated_at_utc`，预期 `bundle_sha256` 与 `manifest_sha256` 怎样变化？只调换
   inputs 的书写顺序又怎样？先按规范化算法推导，再在完整临时副本验证，不修改正本。
3. BMS 新增一个未被 manifest 点名的硬件 ABox。请分别写出“文件存在”“进入候选包”“结构门禁
   通过”“工程分析充分”四个状态的关闭证据，说明为什么前一个不能推出后一个。
4. 把 11.4.1 的闭跳查询移到 AEB。预测它在哪一跳返回空；再说明为什么 AEB 的 SG1 仍可满足
   GATE-CH11-01，以及这条 GATE 没有检查什么。
5. Clause 8 报告模板从 Draft 改成 Approved，其他状态保持 Planned/NotRun/NotPerformed。写出你
   预期 CQ-CH11-03 怎样变化、Claim 是否能关闭，以及应由哪个责任边界审查这次状态修改。
6. 在完整临时副本中做一次分配边单因变异。先记录基线，再移除一个范围内目标派生树的全部
   `allocatedTo`，预测 GATE focus；运行后记录实际签名，恢复并复核。说明这次实验支持的有限能力
   结论和至少两类未覆盖错误。
7. 比较两份结果：bundle 哈希完全相同，capstone 脚本哈希不同，但退出码都为 0。它们能否称为同一
   结论？列出你需要比较的查询、oracle、runtime 和诊断字段。
8. 以 `20260814-ch11-rewrite-diagnostic.json` 的快照身份写一页收口报告，不得重冻。报告须包含
   第一处漂移、离线发现的 10 处漂移
   分类、24 项契约测试结果、未决责任章与边界声明；状态动词只能从 Observed、Failed closed、
   Pending review、Not assessed 中选择，不能写 Accepted。

### 11.9.6 全书最后的人机边界

机器在本书中做成的事情很具体：它能把来源坐标、有限判定表、派生与分配、数值目标、方法矩阵、
例外条件、状态字、输入哈希和已注册反例变成可查询、可回归的合同。它能指出当前图在哪个已编码
条件上不一致，也能拒绝把新字节塞进旧包。

机器不能从这些对账自动推出工程事实正确。S/E/C 查表无误，不证明三维项目判断有充分证据；追溯
命中，不证明需求内容足以承担目标；教学 SPFM 高于目标，不证明 FMEDA 输入可信；EvidenceCandidate
挂进论证，不证明主张成立；签名三元组存在，也不自动创造授权、充分性或法律责任。

建模者要对来源、范围和状态的可审查性负责，规则作者要对能力问题、oracle 和缺陷模型负责，责任章
要对其工程事实与变更负责，具有项目授权的人还要基于真实证据、适用流程和独立性要求作判断。知识
模型可以把这些行为和对象组织得更容易追问，不能替任何角色承担他没有完成的工作。

实际签字时，可以把三种签名并排而不串代。检查器责任人签“这些输入由这些版本的规则执行，机器
观察如下”；工程责任人签“这些对象、依据和未决在我的责任范围内真实、充分到何种程度”；接受或
发布责任人再签“基于前两类记录与适用流程，我作出这个有限决定”。前一签缺失，机器结果不可复核；
中间一签缺失，图里的事实无人承担；最后一签缺失，就只有技术材料，没有授权决定。

三种签名可以得出不同颜色而不矛盾。机器合同全绿，工程充分性仍可 Not assessed；工程活动已完成，
某个报告格式门禁仍可红；两者都满足，出版 release 门禁若未运行，仍不能写 Released。好的报告不是
强迫三者显示同一颜色，而是让每一种颜色都有自己的主语、证据和后续动作。

全书最后能留下的不是一盏永远绿色的灯，而是一条更耐用的纪律：

> 收口不是宣布完成，而是把被检查对象、检查器、当次结果、未决项与效力边界放进同一句可复核主张；
> 门禁能逼已经写进图里的断言按已编码规则对账，却不能证明图外没有遗漏，也不能替有权限的人基于
> 真实证据作出最终判断。
