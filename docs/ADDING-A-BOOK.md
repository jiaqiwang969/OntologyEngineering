# 新增一本标准书

本文定义 OntologyEngineering 的新书接入合同。目标不是“把标准翻译一遍”，而是把
陌生专业领域变成中小制造企业工程师能够学习、查询、验证和受控使用的知识产品。

## 进入条件

开始前必须同时具备：

- 明确的目标读者和制造业使用场景；
- 合法获得的标准或技术资料，以及可说明的使用权限；
- 至少一名能够复核领域实质内容的审阅者；
- 不把书、Skill 或测试结果冒充官方标准、认证意见或合规结论的承诺；
- 私有来源区与公共发布区的物理或流程隔离。

条件不满足时，可以做公开资料调研和 Book Charter，但不得导入受限原文、生成条款级
结论或发布“完整标准书”。

## 第一步：创建书包

```bash
python3 skills/standard-to-book/scripts/init_book.py \
  --slug welding-quality \
  --title "焊接质量工程导读" \
  --standard "目标标准族" \
  --output ./workbooks
```

脚本只创建合同、台账和目录，不读取标准、不调用模型，也不覆盖已有目录。原始标准
必须保存在书包之外的私有受控位置，通过逻辑 ID 和哈希与书包关联。脚手架中的
`.gitignore` 规则只是误操作的最后防线，不代表可以把私有证据放进书包。

创建后先验证结构：

```bash
python3 skills/standard-to-book/scripts/validate_book.py \
  ./workbooks/welding-quality --stage structure
```

冻结 Book Charter 后运行 `--stage charter`；准备公开时运行 `--stage release`。后两者在
未补齐 CQ、来源、审阅和公开资产时应当失败，这正是预期行为。

最终冻结必须在书、命题账、插图、本体制品、书本 Skill、机器测试报告、审阅状态与
`public-assets.csv` 白名单全部完成后执行：

```bash
python3 skills/standard-to-book/scripts/validate_book.py \
  ./workbooks/welding-quality --stage release --write-lock
python3 skills/standard-to-book/scripts/validate_book.py \
  ./workbooks/welding-quality --stage release
```

第一条命令重写 `release/package-lock.csv`，冻结除 lock 自身之外的每个文件；第二条只读
复核冻结结果。此后任一字节变化都会使门禁失败，重新写 lock 应被视为新的候选发布动作。

## 第二步：冻结 Book Charter

在 `book-charter.md` 中确认：

1. 谁会读，读者已有的知识是什么；
2. 要解决哪些制造现场问题；
3. 读完后允许作出哪些决定，哪些决定仍禁止作出；
4. 标准版本、适用范围、排除范围和领域审阅者；
5. 书、知识包、Skill 和 Agent 各自承担什么职责；
6. 公开发布范围和私有证据范围。

没有冻结 Charter，不进入批量写作或生图。

## 第三步：建立来源与权利账

在 `sources/source-register.csv` 为每个来源登记逻辑 ID、版本、哈希、权利基础、是否允许
公开和复核状态。禁止把本机绝对路径、下载令牌、企业名称或原始标准段落写入公共账。

来源账回答“依据来自哪里、当前是否可用”；它不自动回答“解释是否正确”。决定性内容
仍需回到合法持有的原始来源，由领域审阅者核对。

## 第四步：从读者问题建立能力问题

先在 `cqs/cq-register.csv` 写 10–30 个普通工程师会真实提出的问题，例如：

- 这个术语在现场究竟指什么对象？
- 哪个版本、批次、配置或人员身份才是同一个对象？
- 什么活动会产生事实，什么材料只能作为候选证据？
- 哪些条件必须同时成立，哪些例外会改变结论？
- 什么时候必须停止，让专家、审核人或责任人决定？

每个 CQ 都要声明目标读者、需要的证据、预期回答形态和验收方式。CQ 是范围与验收
合同，不是章节标题的装饰。

## 第五步：建立命题账

在 `propositions/proposition-register.csv` 为每个公开命题登记章节、CQ、来源、命题摘要、
命题类别、权限边界、证据判据与审阅状态。摘要必须是原创转述而非受限条文复制。命题类别
明确区分标准依据、作者解释、最佳实践与教学假设；每章和每个 CQ 至少由一个已审阅命题覆盖。

## 第六步：概念化与可执行知识

按领域需要建立：

- 术语表、分类、关系和身份判据；
- TBox 与受控 ABox 的边界；
- 生命周期、状态、版本和权限边界；
- exact query / oracle；
- SHACL 或等价约束；
- 正例、单因反例和回归 runner；
- 来源锚点与未决项。

不要让所有书 import 一个万能总 TBox。跨书对齐应独立登记；移除映射后，每本书的领域
包仍应能够说明自己的范围并独立运行。

## 第七步：用制造现场故事讲明白

正文默认采用“场景先行、误判完整发生、失败暴露、命题后置”的教学节奏：

1. 先让读者看到一个真实感足够、但不泄漏真实企业信息的合成现场；
2. 让常见误判自然发生；
3. 说明误判为什么在当前对象、版本、证据或权限上失效；
4. 再给出标准转述、本体表达和可执行检查；
5. 明确仍需专家判断的部分。

“平民化”是把完整判断链讲清楚，不是删掉条件、例外和责任。

## 第八步：图文协同

每幅图先登记 visual question、semantic baseline、来源/参考图权利、生成方式、哈希、caption
和 alt text，再生成或绘制。图像可以帮助理解，不得补造事故、试验、产品或合规证据。

使用 ImageGen 时，只把已获授权的输入交给服务；公共仓库保存项目自己的提示合同、
规范化结果和发布台账，不保存私人会话、附件临时路径或平台内部实现。

## 第九步：分层放行

发布顺序至少包括：

1. 来源与权利检查；
2. 语义、CQ、约束和正反例检查；
3. 章节问题链与图文一致性检查；
4. 普通工程师冷读；
5. 领域专家复核；
6. 隐私预检和公开资产白名单；
7. 运行本体 runner，形成绑定 runner/manifest 哈希、CQ/命题覆盖、命令、工具和时间的
   机器测试报告；
8. PDF、书本 Skill、版本和 package lock 冻结。

任何自动门禁绿色都只证明当前输入满足已编码合同，不自动授予出版、认证、制造、风险
接受或对外承诺的权限。

## 新书完成定义

一本书只有在以下制品指向同一冻结版本时，才进入候选发布：

- 人可阅读的书与图；
- 可查询的来源地图和命题地图；
- 声明范围内可运行的本体、查询、约束和 fixtures；
- 可复用的 Skill 工作流；
- 来源、权利、隐私、技术和读者审阅记录。

新书注册到总目录时，只增加该领域的来源、概念化、案例、adapter 和工作流；项目总纲
不因某一本书的章节结构而改变。
