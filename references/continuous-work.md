# 连续工程工作：从完整场景到可恢复结果

适用于跨多轮实现、专业工具接续或中断恢复的任务。先按[根目标锚定](goal-anchoring.md)保留原请求、纠正与全部验收，再选择当前场景；一次即可完成的小改动按实际需要简化，不为每个动作建立额外表单。

## 选择最小完整使用场景

从用户要得到的行为倒推一个可执行场景：明确输入与条件、参与对象、关键动作、可观察结果、预期失败和未覆盖范围。范围可以小，但应贯通承担这个行为的相关环节。局部实现或编译成功不能替代场景结果。

例如 CAD 修改场景要贯通“指定对象与修订 → 修改 → 更新 → 保存 → 独立重开 → 回读几何与关联”，只完成编辑接口仍有剩余义务。项目接续场景要贯通“保存意图 → 派发 → 回读 → 更新 Project → 新进程恢复”，并检查条件变化、部分结果和原件丢失后的行为。场景完成后回到根验收，保留其他场景及工程采用所需的独立依据。

开始前核场景是否真的推进根验收，前置是否已成立，什么观察能区分当前解释；依赖不明先调查。不要仅按软件目录或专业分工拆解，然后默认各部分通过就能集成。

## 从同一项目状态派生当前工作说明

当前说明供执行与接续使用，保持短而具体，并链接到原件：

| 当前需要知道的内容 | 正本与接续来源 |
|---|---|
| 根请求、用户纠正、全部验收与本场景的贡献 | route anchor、workspace 原请求及验收 |
| 当前对象、版本、条件、已核前置与未决决定 | 当前 Project、work、来源引用 |
| 待辨假设、下一动作、预期观察与失败后的选择 | exploration 或已有阶段计划；无需重复建计划 |
| 允许执行的范围、尚需用户决定的事项 | 当前会话授权及项目原记录 |
| 实际结果、失败、待执行动作和恢复位置 | 原 owner 回执、workspace HEAD、当前任务视图 |

只派生当前工作所需内容，不复制出第二份可独立修改的状态正本。长任务使用已有 workspace 保存完整义务；压缩或新会话先原生 `resume`，再读取说明。文档摘要不能证明已派发动作完成，旧日志也不等于当前重试授权。

已有冻结探索时，使用[工程关系视图](engineering-reasoning.md)作为这份说明的可核依据。`project explore reasoning` 和 `advance` 返回动作推进的原验收、所检验假设、尚未成立的前提、等待结果及潜在决定影响；workspace 恢复探索阶段时重新派生同一视图。`uncovered_acceptance` 提醒尚无动作直接覆盖的义务。先处理待回读动作，再按冻结顺序推进，失败或未知不得打开需要成功观察的分支。

## 在已有授权内连续推进

当前 Agent 负责理解目标、选择动作、检查结果和修正实现；Rust 核身份、合同、来源与已表达规则。一次局部工具成功后，应继续完成已经授权的场景、验证和交接。一般实现细节、可逆修复、已有范围内的检查无需逐项再问用户。

目标、关键工程前提、验收取舍或外部动作超出已有授权时，再把具体未决事项交给用户；先完成不依赖该答案的工作。不要把参考方法中的交互审批逐层复制成新门槛，也不要把持续工作理解为绕过工程采用条件。workspace 的 `automatic_dispatch=false` 保持：它保存和核对状态，当前会话按授权调用工具。

若任务本来允许并行，只安排输入与写入边界明确的独立活动；共享对象、接口、前置和集成仍回到同一 Project。并行数量不是方法效果的证据，也不是持续推进的必要条件。是否使用子 Agent 由当前宿主与用户授权决定。

## 用分层反馈改变下一步

按当前风险与缺口选择检查，不机械增加全部检查：

- 局部反馈核刚改变的规则或行为，优先运行能复现失败的小范围案例。
- 场景集成贯通真实入口、来源和恢复路径，检查前置变化、部分失败及旧结果的处理。
- 工程验收核对象、工况与独立依据；仿真、同源计算、原生回读和实物计量分别支持各自范围。

失败后记录观察与当前解释，选择能区分原因的下一检查，或撤回本轮改动。再次尝试要有新的输入、诊断、实现或条件依据；不要以相同条件反复执行未明副作用。已派发但结果未知时先回读，保留 `partial`、`unknown` 与原失败，不通过缩减根验收或改写旧回执取得成功。

修复已定位问题后，回归相关失败与完整场景；通过后，只有新改动、失败或未决风险才需要扩展或重复检查。专业工具仍按其原生合同保存、重开或独立检验，不用模型评价替代观察。

## 完成场景后对账并接续

沿[四环承接](design-method.md#在四环之间保持含义和依据)检查需求能否追到模型、承担者与实际证据，结果能否反向追到原主张、条件和来源；全部必要判据是否仍在，是否出现没有目标或依据的动作与产物。复用当前任务视图、route audit、原 owner 和 workspace 的检查；软件维护另可用 `design inspect` 核静态对应。未声明的关系、工程适用性和独立证据充分性仍需研究。

探索结果可按[项目工作区](../docs/PROJECT-WORKSPACE.md)只读回交；必须核完整历史、Project、任务视图与 Harness，不再次调用 `advance`。回执被接收只表示可恢复的阶段结果，待复核决定与根验收继续保留。

一次任务暴露的问题先区分项目实例、软件缺陷和共享方法缺陷。已有表达足够就修实例或记 `no_delta`；跨任务方法候选沿[有证据的改进](regularized-evolution.md)冻结完整目标、基线、候选和评价。对照任务应同时看完成质量、返工、总耗时和成本；局部执行时间、规则符合或一次成功不证明方法收益。
