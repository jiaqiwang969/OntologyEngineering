# 根目标锚定与路线偏移检测

局部严谨不保证路线正确。每一步都核对了来源、版本和范围，整条研究仍可能离开用户最初要的对象与交付物。本文规定 agent 怎样把根目标固定下来、怎样判断偏移、偏移后怎样回来。用户仍只用自然语言提要求；锚定记录由 agent 维护。

## 1. 开始时：固定根请求、根对象和交付物

- **根请求**：逐字保存用户最初的请求及之后每一次纠正，不改写、不概括替代。
- **根对象**：用户真正关心的那个实物、系统或程序（例如“视频里那款工业喷头”）。研究中出现的样件、模型、其他产品都不是根对象。
- **根交付物与验收**：把“研究透”“分析清楚”之类的说法转写成可以核对的交付物和验收项，并请用户确认或在首次汇报中明示。例如“可直接用于仿真的完整结构：功能清单中每一项都有对应结构、尺寸来源和状态”。只写“解释机制”“形成验证路线”而没有交付物时，视为锚定未完成。
- **实物或产品，先做功能分解**：先列出产品必须完成的功能（如供液与回流、驱动、喷射、散热、电气连接、安装与密封），再列出承担每项功能的结构，然后才进入机理研究。功能清单就是“结构是否解析完整”的判据。专利、说明书、视频按“这一功能由什么结构承担”去读。

## 2. 每个阶段：声明关系和贡献

阶段开始前写一行，阶段结束时回填结果：

- 本阶段对象，以及它与根对象的关系：**根对象本身**、**根对象的部件/子系统**、**根对象的模型**、**参照案例**（用其他器件或样件说明根对象的某个机制）、**外部案例**（与根对象只有领域相关性）。
- 本阶段推进哪一项根验收，预期得到什么。
- 参照案例和外部案例必须写**返回条件**：得到什么结论后，回到根对象的哪一项验收、怎样映射。写不出返回条件就不开始这个阶段。

审查（kernel review、来源核对）通过只说明该阶段自洽，不说明它在为根交付物服务；两者分别汇报。

## 3. 偏移判据

出现以下任一情况即判定偏移，停止沿当前方向延伸：

- 连续 2 个阶段的对象不是根对象、根对象的部件或根对象的模型（参照/外部案例连用），且用户未明确同意这次转向；
- 连续 2 个阶段没有推进任何根验收项；
- Project 中出现无法说明与根对象关系的新对象；
- 用户纠正涉及的验收项，之后的阶段没有处理；
- 超过 5 个阶段没有做路线回看。

偏移后：回到验收清单，选择未闭合项中最影响交付物的一项作为下一阶段；确有理由继续外部研究时，先向用户说明原因、预计返回点和代价，得到同意后再继续，并把同意原文记入根请求记录。回到根对象后做一次路线回看（第 7 节），记下偏移段、可复用的方法和不能沿用的结论；回看记录在偏移段之后，该段才算处理完。不能靠删改历史阶段来消除偏移。

## 4. 对简短续接指令的解释

“继续”“按这个思路继续”“不断深入”等简短指令，含义是**沿根交付物推进未闭合的验收项**，不是沿上一轮 agent 自己提出的“下一步”无限延伸。上一轮的建议必须先对照根验收清单核对，不能核对时以清单为准。连续收到相同的简短指令、且没有新的用户信息时，每一轮都要先做第 2 节的声明；多轮没有推进验收项时，按第 3 节停下并在汇报中提出需要用户决定的问题，不再空转。

## 5. 上下文压缩与接续

压缩、换会话或从记录接续时，先恢复根请求原文、根对象、交付物与验收清单、最近的用户纠正和最近一次路线回看，再读方法文字和上一轮下一步。锚定记录保存在 Project 目录内，不依赖会话记忆。重读 SKILL.md 只恢复方法，不恢复目标。

## 6. 约束不是回避根对象的理由

项目约束如“其他型号的文献值不得作为本产品规格”，限制的是**采用方式**，不是要求不碰根对象。正确做法：用带状态的参数（来源确认 / 专利推断 / 视频测量 / 假设）推进根对象的结构或模型，列出待核项及能够核实它们的手段。把研究转到更容易取得完整参数的其他器件上，并不能满足根交付物。

## 7. 路线回看与汇报

每 5 个阶段、每次用户纠正之后、交付前，各做一次路线回看：逐阶段列出对象、关系、推进的验收项和返回情况，标出偏移段及其可复用的方法和不可沿用的结论。阶段汇报的第一句写根验收进度（哪几项已闭合、本轮推进了哪项、还缺什么），然后才写新增来源数、修订号等过程量。

## 8. 机器检查

锚定记录存为 Project 目录下的 `route-anchor.json`（合同 `oev2.route-anchor/1`，由 agent 维护）。当前安装的程序提供 `project route-audit` 时（以安装回执为准），每个阶段开始前、kernel review 之前运行：

```sh
"$OEV2_BIN" --root "$OEV2_ROOT" project route-audit \
  --input var/projects/<id>/project-rN.json --anchor var/projects/<id>/route-anchor.json
```

输出 `oev2.route-audit/1`：`anchored` 退出 0；`drift` 或 `invalid` 退出 1，并列出发现代码、阶段和说明，以及未闭合验收项和未锚定对象。连续离开根对象或未推进验收的一段，在其后登记路线回看（`reviews`）之前一直报 drift；回看之后再次离开会重新判定。drift 或 invalid 时不进入下一阶段，先按第 3 节处理。策略参数只能比默认更严格（`off_root_stage_limit` ≤ 2，`no_progress_stage_limit` ≤ 2，`review_interval` ≤ 5），放宽即判 invalid。

最小记录（除 `after_stage`、`return_to`、`approval` 可省略外，字段均必填）：

```json
{"schema":"oev2.route-anchor/1","project_id":"<Project ID>","root_object":"<根对象ID>",
 "deliverable":"<可核对的根交付物>",
 "requests":[{"id":"U1","kind":"root","text":"<用户原话逐字>","source":"<会话与时间>","affects":[]}],
 "functions":[{"id":"F1","statement":"<功能>","structures":["<承担结构>"]}],
 "acceptance":[{"id":"A1","statement":"<验收>","functions":["F1"],"status":"open"}],
 "stages":[{"id":"S01","object_id":"<对象ID>","relation":"component","relation_target":"<根对象ID>",
            "advances":["A1"],"outcome":"pending"}],
 "reviews":[],
 "policy":{"off_root_stage_limit":2,"no_progress_stage_limit":2,"review_interval":5}}
```

`relation` 取 root / component / model / reference_case / external_case；参照与外部案例加 `"return_to":{"acceptance":"A1","condition":"…"}`，用户同意转向时先在 `requests` 记一条 `kind:"approval"` 的原话，再在阶段上写 `"approval":"U5"`。用户纠正记为 `kind:"correction"`，`affects` 写受影响的验收项，之后必须有阶段推进它们。

程序只检查已声明的关系与计数规则；关系声明本身是否真实、交付物是否合格，仍需原件和独立验证。未安装该命令时按本文逐条人工核对，并在汇报中说明未经机器检查。

### 交付范围：`oev2.route-anchor/2`

工具结果登记后、决定已用 `project decide` 更新（见[专业能力](professional-capabilities.md)的回交命令），锚定记录改用 `oev2.route-anchor/2`。每个验收项增加 `decisions`（支撑它的 Project 决定）和 `evidence`（已登记的证据 ID，如 `tool-result:<result_id>`），`status` 取 open / partial / closed / blocked：

```json
{"id":"A1","statement":"<验收>","functions":["F1"],"status":"closed",
 "decisions":["D-…"],"evidence":["tool-result:<result_id>"]}
```

`project route-audit` 按 `schema` 自动选择 /1 或 /2。/2 输出 `oev2.route-audit/2`，在 /1 的全部检查之外给出交付范围：

- `delivery_verified`：标为 closed 且满足以下条件的验收项，只有它们可以汇报为已交付：所列决定都是 supported，依据已登记；决定仍绑定对象的当前修订，来源仍在 Project 中；所列证据都已登记。
- `delivery_open`：未关闭的验收项，继续调查或补验。验收项可以列出 `memory-candidate:` 证据作参考，但记忆证据不计入关闭。
- `delivery_inconsistent`：标为 closed 但依据不足的验收项，整份报告为 invalid。先改回未关闭或补足证据，不得交付。

被分析的代码或制品改版时，agent 在 Project 中登记新的对象修订和来源，用 `project reconcile` 列出需重审的决定。此后绑定旧修订的决定不再支持交付（`decision_object_stale`）：在新修订上重新运行工具、登记结果，再用 `project decide` 更新决定。程序只核对声明、登记与绑定关系。`evidence` 只核是否已登记；交付物是否合格、工程能否采用，仍需另行验证。

## 反例来源

本文来自一次真实偏移（私有维护记录 `route-anchor-goal-drift-01`，不进入分发）：从一个产品视频出发，第 3 阶段换成参数更齐全的历史样件模型，随后沿“补最大未知”的链条转到其他器件的感测、补偿、固件和材料，每阶段审查都通过，直到用户纠正才回到产品结构。逐阶段回放时，`project route-audit` 在第 3 阶段即报告偏移。该案例已暴露，只能作为开发回放，不能证明本文方法的泛化收益。
