# OntoClean 元属性标注与类层次质量检查
# OntoClean Metaproperty Analysis (Guarino & Welty, 2002)
#
# OntoClean 用"元属性"审查类层次的合理性：
# 不看类的内容，只看类的形式性质，即可发现建模错误

# ==============================
# 1. 四个核心元属性
# ==============================
# 刚性（Rigidity）
#   +R  刚性：实例永远是该类实例（Equipment：一台车床永远是设备）
#   ~R  反刚性：所有实例都可能不再是该类实例（Idle：空闲是临时状态）
#   -R  非刚性：部分实例可变（Hard：有些硬的东西会变软）

# 同一性（Identity）
#   +I  携带同一性判据（Equipment：序列号判定"是不是同一台"）
#   -I  不携带（Red：红色的东西之间没有统一的同一性判据）

# 统一性（Unity）
#   +U  有统一的整体边界判据（Machine：一台机器边界明确）
#   -U  无（Metal：一摊金属没有"一个"的判据）

# 依赖性（Dependence）
#   +D  外部依赖：概念成立依赖其他实体存在
#       （Operator 依赖被操作的 Equipment）

# ==============================
# 2. 制造本体标注示例
# ==============================
#   类                      R     I     U     D    说明
#   --------------------    ---   ---   ---   --   ------------------
#   Equipment               +R    +I    +U    -D   本质类型
#   CNCLathe                +R    +I    +U    -D   本质类型
#   Material                +R    +I    -U    -D   物质，无统一边界
#   IdleEquipment           ~R    +I    +U    -D   状态（临时）
#   BottleneckResource      ~R    +I    +U    +D   角色（依赖调度上下文）
#   Operator                ~R    +I    +U    +D   角色（人担任）
#   SparePart               ~R    +I    +U    +D   角色（相对整机而言）

# 直觉：
#   "类型"（+R）回答"它是什么"——车床永远是车床
#   "角色/状态"（~R）回答"它当前充当什么"——空闲、瓶颈、备件

# ==============================
# 3. 核心检查规则
# ==============================
# 规则1（刚性约束）：刚性类不能以反刚性类为父类
#   +R 类 ⊑ ~R 类  → 违规
# 规则2（同一性约束）：子类必须继承父类的同一性判据；
#   携带不相容同一性判据的类之间不能有包含关系
# 规则3（统一性约束）：有统一性的类不能以反统一性类为父类

# ==============================
# 4. 典型违规与修正
# ==============================
# 违规示例1：
#   Equipment(+R) ⊑ Resource(~R)
#   "设备是资源"——但 Resource 是调度语境下的角色（反刚性），
#   设备是刚性类型，刚性类挂在反刚性类下，违反规则1

# 修正：用"角色扮演"关系替代继承
#   Equipment playsRole ResourceRole
#   （类型层次与角色层次分离，角色通过对象属性关联）

# 违规示例2：
#   CNCLathe ⊑ IdleEquipment ?
#   把状态建成父类——车床会运行，届时不再是"空闲设备"

# 修正：状态用数据属性或状态个体表达
#   Lathe_003 hasStatus Idle      # 状态可变，不进类层次

# 违规示例3：
#   Equipment(+U) ⊑ Metal(-U) ?
#   "设备是金属"——混淆了"由金属构成"与"是金属"

# 修正：构成关系不是继承
#   Equipment madeOf MetalMaterial

# ==============================
# 5. 工程化使用建议
# ==============================
# 不必对全本体做完整标注——成本高；
# 推荐在以下时机做局部OntoClean审查：
#   (1) 类层次初版评审时：只标注 R（刚性），揪出"角色当类型"
#   (2) 两个本体合并时：检查同一性判据是否冲突
#   (3) 推理出现反直觉结果时：用元属性定位概念混淆
#
# 经验法则（覆盖80%问题）：
#   会"变回去"的概念（状态/角色/阶段）不要放进 rdfs:subClassOf 层次，
#   用属性（hasStatus / playsRole / hasPhase）表达
