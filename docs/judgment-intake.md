# 共用批量判断与证据审查

本模块把反复出现的原文判断交给 Jev，把工程证据义务交给 Semantica。
当前只提供候选和有界语义审查；尚未取得独立评测支持的自动采用资格。
高 confidence 不能代替来源、条件、原生检查或工程判断。

## 职责与模式

两卷书指导“怎样提问”；[来源与能力地图](../references/judgment-pattern-source-map.json)
记录精确书源摘要和已实现范围。第二卷的行业示例建立在第一卷的对象、身份、关系、
CQ 和证据方法上；不把 ISO 派生领域规则当成跨行业普遍要求。

| 共用模式 | 工程上要问什么 | 本版能执行什么 |
| --- | --- | --- |
| P-ID 身份 | 是同一个对象、实例和版本吗？ | 明确标识与修订匹配；仅名称或模型匹配保留未知 |
| P-CLAIM 主张 | 谁说过，与内容成立分别有什么依据？ | 来源发言、工程主张与模型候选的依据角色检查 |
| P-SCOPE 范围 | 证据覆盖哪个情境，哪些条件尚未成立？ | 已声明范围、条件、局部完整性和表示适用性 |
| P-REALIZE 实现 | 必要功能有实现方式和适用检查吗？ | 对实际原生 review 的有界覆盖汇总 |
| P-CHANGE 变化 | 哪条支持关系失效，哪些输出需重审？ | 版本、挑战与重审记录；已记录支持依赖的闭包查询 |

正式问题含义、CQ、query、shape、规则和案例来自 `runtime/semantic-bundles.json`
锁定的 Semantica 包。OE 提供源定位、类型检查、传输和执行记录。SQLite 是任务台账，
不保存第二套本体权威。五组模式可同时相关；强制单选会丢掉义务。

## 批量初判

使用根 `runtime/.venv/bin/python scripts/judgment_batch.py --help` 查看参数。

1. 用 `catalog` 读取受控目录。当前有 13 个独立 Choice 问题，包含支持范围、身份、
   变化、四种可重叠资料角色及五组模式相关性；每项保留 `not_established`。
2. 参照[合成批次](../examples/judgment_intake/batch.json)列出原文 SHA、JSON Pointer
   或文本范围、资料血缘、对象版本、主张、CQ 与必查方法。原生 CAD、图纸图片和
   音视频须先由专业工具提取；此入口不声称读懂未提取的原件。
3. `init-lock --model <精确版本> --output <新文件>` 固定模型、问题、分段方式、
   合批/并发策略、适配代码和语义包。生成的组合始终是未验证的影子配置。
4. `prepare --input … --evidence-root … --lock … --output …` 验证清单；
   `run` 另需 `--journal …` 和本地 `--credential-file …`。凭据文件须由当前用户
   持有、权限为 0600；值不写进代码、配置锁、台账或分发件。
5. 同一原文可一次多问；依赖前答的问题分阶段。超长输入要求明确重选范围，
   不静默截断。恢复使用同一批次、输入和完整配置；不同配置另开批次。

只将已授权向该服务发送的资料加入清单。凭据路径与项目材料留在私有工作区。
未配置 Jev 时可继续原生工程工作，并如实报告模型未执行。

台账区分 `candidate / unknown / execution_error / pending`，四项总量等于事先
声明的问题数。失败有界重试，部分成功保留，首个有效候选不可被迟到结果覆盖。
请求发出前写入开始记录；崩溃后可能重发未确认请求，不能宣称上游只收费一次。
缓存按项目、权限范围、来源、问题和完整配置隔离，并明确标记 replay。

所有未知、请求失败、候选冲突和不完整上下文进入复核队列；另外按领域、问题、
答案及分数区间抽查，覆盖高分和“不相关”输出。这里的分数区间只用于抽样。
批次完成表示判断已返回，未执行的必查方法仍留在队列里。

## 从候选到审查

`scripts/judgment_review.py` 使用同一原生 `semantic_engagement.review` 入口。
每次都需要当前项目的精确 promoted binding、workspace 与 actor；源哈希或绑定过期
即拒绝执行。分发的包运输件与作者案例回归不能替代接收方的项目采用。

- `candidates`：从台账读取请求和原始响应，重核来源、版本、问题与候选 ID；
  将支持和反驳都作为 `model_candidate` 投影。候选审查不能代替必需工程审查。
- `plan`：读取[CAD 审查计划](../examples/judgment_intake/cad-review-plan.json)
  或[工艺成本审查计划](../examples/judgment_intake/process-review-plan.json)。每项检查
  绑定同一主张、范围和配置，并实际执行。功能覆盖只使用本次返回且身份匹配的结果，
  不接收外部 PASS 清单；缺少检查和空清单不能算覆盖。
- `impact`：读取[来源绑定的依赖记录](../examples/judgment_intake/impact-record.json)，
  由 Semantica 查询需重审的主张、推荐、报价和交期。`support_dependency` 表示结论
  依赖；`physical_hypothesis` 单独保存，不能沿它自动宣判实物失败。

“字段来自受控记录”仍是有来源的工程断言，不是对提供者的身份认证。
`source_verified` 仅表示所选字节与摘要一致；`clear` 仅表示该投影未出现所查语义缺口。
本组件不负责事实批准、产品放行或成本批准。正式 ABox 可记录“某人提出某主张”这一
发言事件，而不接受其物理内容；候选标注不得以普通事实边混入已采用断言。

## CAD、工艺与成本怎样共用

CAD 保留对象/实例、配置、接口、回读和模型条件；制造模块接续功能、路线、检验、
物料数量口径、费用和交付。两侧引用同一对象与来源 ID，使用同一问题目录及语义包。
具体数值、CAD 几何求解与成本算术继续由相应专业工具承担。

合成示例检验旧版报告支持新版、旧报价未重审、理想贴合冒充真实界面、规定运动
冒充驱动能力以及有效量替代实际投料等失效。它们说明查询是否识别已知缺口，
不是焊接、装配或某种机构普遍不可行的结论，也不是独立准确率基准。

## 更新、恢复与学习

模型、问题、候选目录、选择范围和语义包分别定位变更。完整配置变化后旧台账不能
继续执行；旧响应只作有版本的历史记录。重新运行需新批次和新评测，不能继承旧阈值。
对相同问题比较单问与合批时，分开报告使用量、完成率、未知、分歧及人工复核成本。
没有人工/OCR/专业计算费用与独立评测，不能声称端到端降本或准确率提高。

使用 `scripts/judgment_evaluation.py audit` 核对评测集，`evaluate` 读取精确配置下的
原始候选台账。输入格式见[开发样例评测集](../examples/judgment_intake/evaluation-development.json)。
同源根、同一文件的副本不能跨开发/校准/留出集；已用于修改系统的资料保留开发标记。
独立参考需另有审阅记录与审阅人，模型标签和开发者自己的答案不计为独立参考。
审阅人身份由外部控制面核实，此工具只检查记录关系。输出分问题、领域和参考质量的
观察一致率、类别 precision/recall 及混淆表；未返回的判断仍计入分母，多种可接受
答案不强改成单一真值。没有独立标签时不产生独立准确率或采用资格。

`cost` 模式读取费用台账，按已声明数量与单价计算记录小计，并明确保留未知项。
缺少人工、OCR 或专业工具费用时总成本为未知，不能用已知 API 小计冒充总成本。
`retrieval_audit` 可对照完整目录、检索候选与参考集合，分别报告漏召回和目录缺项；
这个记账结果不创建本体增量。

语义升级沿根 skill 的原生治理流程。保留旧 CQ 定义，新义务追加扩展 CQ。晋升后
另存并采用返回的 successor binding；旧 binding 仍可查历史，不能用于当前执行。
语义恢复须产生经治理的后继版本或经过验证的独立历史环境，不能覆盖 registry 文件。
若采用隔离环境，恢复时核对完整包摘要。用相同版本号重新从零编写的包仍可能具有
不同的增量和来源身份，不能配旧运输件。开发恢复演练已通过原生 API 重放精确版本链、
另存采用绑定，并在冻结的解包环境中恢复完整配置；恢复后的新请求与历史缓存分开记录。
这项演练验证执行一致性，不授予模型质量资格，也不证明任意运行时降级可用。

经验先分为提取错误、模型误判、项目缺证、适用范围错配或语义缺口。前四类修正
对应记录/配置；可复现、可迁移的语义缺口才进入 `domain-ontology-loop`。
大量重复判断不会自动成为 TBox。项目材料、凭据、原始响应与人工参考标签留在
私有目录；公开内容只收通用代码、受控包及明确标注的合成示例。
